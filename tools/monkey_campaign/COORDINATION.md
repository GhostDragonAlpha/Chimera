## Heartbeat: top of each hour, Windows system Central Time

The operator chose the system clock and aligned hourly boundaries. Windows was checked
as `Central Standard Time` / Central Time (US & Canada), with daylight saving enabled
by the system's normal zone rules. Display local time with its UTC offset; retain UTC
for unique window identity, including the repeated autumn hour. Do not hard-code CST
as UTC-6 year-round.

Every assignment expires at the NEXT top of the hour. An agent registering at 14:40

This is not a rolling 60 minutes and not a promise of a full hour for a late join.
Progress reports do not move the deadline.

At :00 the coordinator checks all ten slots and its lead-instruction revision. Save
checkpoints BEFORE that boundary. The registry marks expired assignments
EXPIRED_RECOVERY_REQUIRED and rejects their normal progress updates. It preserves
the last checkpoint/memory and keeps the slot occupied. Time expiry is not proof the
agent, build or child process actually stopped.

For each expired slot:

1. Request that the owned worker stop/checkpoint through the existing execution mechanism.
   Fence its native claim/publication path through the existing authority where available.
2. Confirm actual worker completion/cessation and preserve unique work/evidence. Never
   infer cessation from silence, kill by process name, or terminate an unrelated/protected
   training job. Long training is a separately owned job, not a disposable agent lease.
3. Release using the exact old slot/generation and preservation reference with a truthful
   `worker_finished_confirmed: true`. That stores a last_handoff and frees the model slot;
   it does NOT release native worktree/GPU ownership or delete files.
4. Register the same agent for an authorized new bounded assignment or assign a replacement,
   which receives a new generation and the next hour deadline. Stale generations refuse.

If cessation cannot be established, retain the recovery hold and use other eligible
slots. A hard time boundary revokes this reporting assignment; it cannot by itself revoke
filesystem writes by a process sharing the operator's Windows account.

Deadline checks run whenever this helper is invoked. No background watcher or automatic

## GPU handoff: training can preempt gaming and local inference

**Operator override, 2026-09-24: "Training may interrupt gaming too."** Any authorized
worker can request training resources; only the existing resource supervisor executes
the handoff. This supersedes older gaming-priority wording for an admitted training
request. It is not permission to kill unrelated applications, widen task scope, or
start an unqualified training experiment. Derivation, training gates and resource
admission still apply. No popup is required for a handoff already authorized by this
policy; an unsafe/unavailable adapter must block with evidence rather than guess.

### Priority and authority

1. An already-running protected training job retains the GPU until it completes,
   fails with observed cessation, or receives an explicit authorized stop. A new
   training request cannot steal it. The hourly agent lease does not own this lifetime.
2. Eligible training requests take priority over gaming and local-model inference.
   Multiple training requests serialize fairly; do not let arbitrary worker priority
   numbers jump the queue or restart the drain. Validate the native task and generation.
3. During gaming with no admitted training request, local GPU inference waits unless
   a tested resource allowance explicitly permits it. Cloud/CPU work may continue.

Extend the existing `rtx4090` authority and queue; do not add a rival GPU lock file or
allow each of ten agents to run unload/kill commands independently. GPU demand is a
resource request inside an existing assigned task, not permission to edit the sealed
scope. The resource supervisor must run independently of Bionic's/local model's ability
to generate tokens, so a local requester can be checkpointed and unloaded without
losing the controller that will later resume it. This supervisor is ordinary bounded
control software, not a recurring Astra/LLM session.

### Required handoff sequence

`REQUESTED -> DRAINING -> READY -> TRAINING -> RESTORING -> AVAILABLE`

Any uncertain/failing transition enters `RECOVERY_HOLD`; it never fabricates READY.
Transitions, current owner, task/generation, job identity, evidence and next action
must be visible through the existing controller and coordinator's slot/report pointers.

1. **Request and validate.** Record the training brief, derivation/gate receipt, required
   VRAM/headroom, expected duration, actual requester, native task/generation and existing
   training owner. Atomically reserve the transition against competing requests.
2. **Close inference admission.** Gate every participating client path before draining:
   Bionic/pi requests, the Python LM gateway, judges and automatic model loads. Requests
   wait as RESOURCE_WAIT without spending a model-load timeout or falling through to
   direct inference. Disabling only one Python caller is insufficient. Prove that JIT
   reload and retries cannot bypass this gate throughout training.
3. **Checkpoint local workers.** Preserve actual session/transcript identity, tool/action
   state, dirty work, owned child jobs and next action. Stop issuing new local-model
   calls; drain existing generation/tool work to a safe boundary. Model unloading does
   not itself save an agent session. A model may not coordinate its own eventual restart.
4. **Release gaming.** Prefer an application-supported save/quit or safe release method
   for the specifically registered game (verified executable, PID and start time).
   Pausing/minimizing a game is not proof it released VRAM. A process-name match or
   foreground window alone is not sufficient identity. Never automatically escalate
   a failed graceful release to a forced kill; report RECOVERY_HOLD. Forced termination
   that risks unsaved work requires a separate explicit operator instruction. No blanket
   taskkill, GPU reset, unrelated app termination, or hidden relaunch of games.
5. **Unload model instances.** Capture each exact instance ID and its restoration
   configuration: model artifact, context, offload/load settings and worker associations.
   Use the tested LM Studio management API/CLI to unload named instances. Avoid `--all`;
   do not stop Bionic's entire application or discard its conversations as a substitute.
   Verify unloaded state and observed VRAM availability. A success message or TTL is
   insufficient; idle timeouts are not a training lock.
6. **Grant and launch once.** Confirm inference admission remains closed, game release
   succeeded, sufficient usable VRAM exists with display/driver headroom, and no other
   protected job holds the resource. Commit the grant through the native controller,
   then start the authorized job exactly once with a durable run ID. On Windows the
   display still uses GPU resources; do not require zero total VRAM or claim an OS-wide
   hardware lock. Track contention; mark performance measurements invalid if it occurs.
7. **Release and restore.** Observe training process/child cessation and preserve its
   receipts/checkpoints before release. Do not free the GPU on worker silence, a lease
   timeout or supervisor restart. Service already-admitted training requests without
   pointless unload/reload cycles. When eligible for inference again, reload only the
   required saved local-model configuration, confirm health and resume each preserved
   worker once at its next checkpoint with a current slot generation. Do not launch a
   test prompt that changes user conversations. Games are not automatically relaunched.

If the host/supervisor crashes, recover the journal and inspect real process/model/native
claim state. Unknown state stays RECOVERY_HOLD. Never assume a stored lease implies a
live process, an expired lease implies death, or a restart authorizes replaying launch.
