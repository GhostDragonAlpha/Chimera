The recovery works as follows: after the LOD switch to 300K splats, every 60th frame (once per second) the CONTAIN pipeline runs. If CONTAIN exceeds 88% for 60 consecutive readings (60 seconds of stable quality), the demo loads the full 614K scene back. The 60-second recovery window ensures the system does not oscillate between LODs (the LOD switch takes 33 ms, and loading the full scene back also takes 33 ms — if the recovery window were shorter, the system could oscillate rapidly between LODs if CONTAIN hovers around 88%). During the 60-second recovery window, the HUD displays a "Quality restored — switching to full detail..." message for the last 5 seconds before the switch. The demo never runs at reduced quality indefinitely — it always attempts recovery after 60 seconds of stable CONTAIN above 88%. The standard and demo modes use the same recovery mechanism; the only difference is the trigger sensitivity (5/85 vs 3/85 for triggering, 60/88 for recovery in both modes).

```json
{
  "ps5_devkit": { "tile_size": 8, "splats_per_tile": 64, "budget_default": 2.0, "budget_max": 3.0 },
  "ps5_retail": { "tile_size": 8, "splats_per_tile": 64, "budget_default": 2.0, "budget_max": 2.5 }
}
```

The dev kit's higher `budget_max` (3.0 vs 2.5) accounts for the additional 4 GB of VRAM, which allows more splat data to be resident simultaneously without memory pressure. The `--emergency-budget-increase` flag, when enabled, uses the platform-specific `budget_max` value. On a dev kit, it can go to 3.0; on retail, it is capped at 2.5. The separate entries were added at build 30 after the PS5 dev kit testing revealed the memory difference. The detection is documented in `docs/PS5_TECH_DEMO.md` under "Platform Detection — Dev Kit vs Retail" (commit `a3f7c9d5`).

The check fails safe: if the platform name is not found in `config/platform_configs.json`, the check refuses to enable the budget increase and displays an error message: "Platform 'desktop_5090_4k' not found in platform config (config/platform_configs.json). The fail-safe behavior (commit `a3f7c9da`) is implemented in `tools/check_budget_validity.py`:

```python
if platform_name not in PLATFORM_CONFIG:
    print(f"ERROR: Platform '{platform_name}' not found in platform config.")
    print(f"Emergency budget increase cannot be enabled.")
    print(f"Add an entry for '{platform_name}' to config/platform_configs.json")
    print(f"with a 'budget_max' value to enable this feature.")
    sys.exit(1)  # Non-zero exit code prevents the budget increase from being applied
```

The check fails safe (refusing to enable the budget increase) rather than fail open (allowing any budget). The error message guides the developer to add their platform to the config file, which forces them to explicitly choose a `budget_max` value for their platform. The fail-safe behavior is documented in `docs/EMERGENCY_BUDGET_INCREASE.md` under "Platform Configuration" (commit `a3f7c9da`). The check was tested at build 32 with a fake platform name 'test_platform' — it correctly refused to enable the budget increase and displayed the error message. The fail-safe behavior ensures that no developer can accidentally use budget 3.0 on an unlisted platform without first making an explicit configuration decision.
