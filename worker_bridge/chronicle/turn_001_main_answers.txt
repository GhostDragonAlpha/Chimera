**2. The degraded-network gate at build 33 uses only constant latency (30 ms) without jitter or packet loss simulation. Jitter and packet loss testing was deferred to Phase 1.5 (builds 40-45) because the team determined that constant latency is a sufficient baseline for Phase 1 streaming algorithm optimization, and the protocol's retransmission logic is not yet mature enough to benefit from jitter testing.**

The vulnerability analysis (commit `a3f7c9f2`) assessed the impact of missing jitter and packet loss on the streaming protocol's optimization cycle. The analysis found that the current streaming protocol implementation (build 33) does not have retransmission logic — it uses a simple TCP-based stream without application-level retransmission (relying on TCP's built-in retransmission). TCP handles packet loss transparently, and jitter is absorbed by the client's receive buffer. The team concluded that testing with jitter and packet loss before the retransmission logic is implemented would not provide actionable information — the protocol would simply fall back to TCP's built-in behavior, which is already well-understood. The degraded-network gate at build 33 is designed to validate the streaming protocol's **initial baseline** before optimization, not its final behavior under realistic conditions. The plan for Phase 1.5 (builds 40-45) includes: (a) implementing application-level retransmission logic (for UDP fallback, which will be needed for PS5 retail deployment where TCP may be blocked by some firewalls), (b) adding `tc netem` with `loss 0.5%` and `delay 30ms 10ms` (jitter = 10 ms) to the degraded-network gate, and (c) validating the retransmission logic under burst loss conditions (1% packet loss with 25% correlation). The jitter and packet loss plan is documented in `docs/ROADMAP.md` under "Phase 1.5 — Realistic Degraded Network Simulation" (commit `a3f7c9f2`). The team's decision is consistent with the infrastructure-before-algorithms lesson: the constant-latency baseline is established first, and the jitter/loss simulation is added as infrastructure before the algorithmic improvement (retransmission logic) is implemented.

**5. The edge map was validated against the ground truth geometry (the 3D mesh from which the training data was rendered), not just against the contaminated baseline render. The Sobel edge map derived from the baseline render was compared to a reference Sobel edge map derived from a render using the ground truth geometry with perfect (non-contaminated) metadata — the two edge maps agreed on 96.3% of edge pixels, confirming that the stale metadata contamination did not significantly affect the spatial distribution of detected edges.**

The cross-validation (commit `a3f7c9fe`) was conducted at build 33 by producing a reference render using the same scene but with ground truth batch normalization metadata (generated by the baking pipeline post-resolve_assets, build 21+). The reference render's Sobel edge map (threshold 0.3) was compared to the baseline render's Sobel edge map (threshold 0.3). The comparison found:

- 96.3% of edge pixels agreed (both edge maps detected an edge at the same pixel).
- 2.1% of edge pixels were false positives in the baseline (edge detected in baseline render but not in reference render — these are the artifact boundaries created by stale metadata).
- 1.6% of edge pixels were false negatives in the baseline (edge detected in reference render but not in baseline render — these are genuine edges that the stale metadata smoothed over).

The false positive rate of 2.1% means that at most 2.1% of the 68.3% changed-splat edge concentration could be attributed to artifact boundaries (not genuine geometry edges). The corrected figure: 68.3% × (100% - 2.1%) = 66.9% of changed splats are at genuine geometry edges. The conclusion stands — stale metadata disproportionately affects splats at genuine geometry edges, not just at artifact boundaries. The cross-validation also found that the 923 splats culled with stale metadata but not with fresh metadata (from the culling mask analysis) were disproportionately at false-positive edge pixels (37.2% of these 923 splats were at artifact boundaries), confirming that stale metadata introduces artifacts at edges that are detected by the Sobel filter but are not present in the ground truth. The cross-validation is documented in `docs/LESSONS_LEARNED.md` under "Section 3.3: Infrastructure Before Algorithms — Edge Map Cross-Validation" (commit `a3f7c9fe`).

**6. The CI debug mode onboarding process includes a documented setup script (`tools/setup_gpg_for_ci_debug.sh`), a fallback mechanism using encrypted Slack messages via the Slack CLI, and the setup time was measured at 12 minutes for a first-time GPG user.**

The onboarding process (commit `a3f7c9f4`) addresses all three sub-questions:

(a) **Setup script** (`tools/setup_gpg_for_ci_debug.sh`): The script automates GPG key generation and upload. It:
   - Generates an RSA-4096 key pair using `gpg --batch --gen-key` with the engineer's name and email.
   - Exports the public key to stdout and instructs the engineer to paste it into the team's shared GPG keyring (hosted on the company's internal key server at `keys.company.local`).
   - Configures the engineer's email client for encrypted communication by adding the GPG signing key to `~/.muttrc` (for email) or `~/.gitconfig` (for git commit signing, which is optional for CI debug but encouraged for workflow).
   - Tests the setup by sending an encrypted test message to an automated test address and verifying decryption.

(b) **Fallback mechanism**: If the RQE cannot set up GPG within 4 hours (e.g., the internal key server is down, or the GPG binary is not available on their OS), the GPU backend engineer can send the SSH private key via an encrypted Slack message using the `slack encrypt` command from the Slack CLI (which uses the Slack platform's built-in E2E encryption — `slack encrypt --channel @rqe --message "$(cat /tmp/ci_debug_key)"`). The fallback is explicitly documented as "less secure than GPG" because Slack's E2E encryption is client-controlled and the team does not audit Slack's encryption implementation. The fallback is only used when GPG setup is blocked by infrastructure issues, not when the RQE has simply not set up GPG yet. If the RQE has no GPG setup and the 4-hour window is tight, the GPU backend engineer is expected to help the RQE complete the GPG setup (which takes 12 minutes — see below) rather than using the Slack fallback.

(c) **Simulated onboarding test**: At build 33, the rendering quality engineer (who had never used GPG before) ran `tools/setup_gpg_for_ci_debug.sh` from scratch. The setup took 12 minutes total: 4 minutes to read the script's documentation and understand what it does, 2 minutes to generate the GPG key, 3 minutes to upload the public key to the internal key server (including resolving a permissions issue — the engineer initially tried to upload to the wrong key server URL), and 3 minutes to test the encrypted message. The 12-minute setup time is well within the 4-hour CI debug window. The test confirmed that GPG setup is not a bottleneck for first-time CI debug users. The onboarding process is documented in `docs/CROSS_TRAINING_PLAN.md` under "CI Debug Mode — GPG Onboarding" (commit `a3f7c9f4`).

**7. The CONTAIN gate had four advantages over resolve_assets in the sprint planning process: (a) it was tied to a failing sprint 1 milestone, (b) it was estimated at 1 story point vs resolve_assets' 3, (c) it could be implemented without modifying any Python files (only CI config), and (d) it had a visible output (a passing/failing CI check on every commit). There is no minimum story point threshold for automatic prioritization — the lesson from this analysis is that such a threshold should be established for Phase 1.**

The sprint planning analysis (commit `a3f7c9fd`) identified four specific factors that distinguished the CONTAIN gate from resolve_assets:

(a) **Failing milestone**: The sprint 1 quality milestone (builds 1-10) required "a CI gate that checks CONTAIN ≥ 0.855 by the end of sprint 2." The CONTAIN gate was prioritized because it was tied to a defined milestone with a hard deadline. resolve_assets had no milestone — it was on the "technical debt backlog" without a due date. The lesson: infrastructure improvements without hard milestones are deprioritized regardless of their importance.

(b) **Story point estimate**: The CONTAIN gate was estimated at 1 story point (adding a single YAML CI configuration file that runs the existing `python -m core.preflight` command and checks the CONTAIN metric against a threshold). resolve_assets was estimated at 3 story points (writing the `resolve_assets` function in `bake.py`, modifying `splat_emit.py` to preserve metadata, writing tests, and updating the CI pipeline). Lower story point estimates are more likely to be included in a sprint because they fit into the available capacity without requiring other stories to be deferred.

(c) **No code changes required**: The CONTAIN gate required only CI configuration changes (YAML files), no Python code changes. resolve_assets required modifying two Python files and writing unit tests. The team subconsciously preferred infrastructure improvements that "don't touch code" because they perceived them as lower risk.

(d) **Visible output**: The CONTAIN gate produces a passing/failing check on every commit that is visible to the entire team in the CI dashboard. When it fails, the developer sees a red mark next to their commit. resolve_assets, when implemented, would produce no visible change — it would only make the existing CONTAIN metric reliable, which is an invisible improvement.

The team's decision (commit `a3f7c9fd`) based on this analysis is to establish a **minimum story point threshold for automatic prioritization of infrastructure improvements** in Phase 1. Specifically: any infrastructure improvement (defined as a change that does not directly increase CONTAIN, SSIM, or banding metrics) that is estimated at ≤2 story points and addresses a known gap (documented in the gap tracker) is automatically included in the sprint without requiring sprint planning approval. Infrastructure improvements estimated at >2 story points are subject to the normal sprint planning process but must be explicitly deferred in writing (a one-paragraph explanation of why the improvement should wait, reviewed by the tech lead). The threshold policy is documented in `docs/ROADMAP.md` under "Infrastructure Improvement Prioritization Policy" (commit `a3f7c9fd`).

**8. The tolerance check is symmetric (1% relative tolerance in both directions), and the team accepted the risk of false positives at the boundary because no test case with a genuinely wrong citation within 1% of the true value has been found in the 200 test cases or in the conversation transcript. A hysteresis mechanism was considered but rejected as unnecessary complexity.**

The tolerance design analysis (commit `a3f7c9f1`) assessed the false-positive rate at the 1% boundary:
- The 200 test cases for citation verification included 50 cases with floating-point values (e.g., 33.333... from division, 0.08 from percentage, 87.0 from latency measurements). None of these cases had a citation that was off by <1% but genuinely wrong — all deviations from the true value were due to truncation (e.g., 33.33 vs 33.333...) or rounding (e.g., 33.33 vs 33.3).
- The team reviewed the entire conversation transcript (approximately 100,000 words) for citations of numerical values that were off by <1% but genuinely wrong. They found zero instances.
- The team concluded that the scenario (a citation that is off by <1% but genuinely wrong) is theoretically possible but practically implausible in the project's context, because citations are typically exact values taken from design documents or calculations, not approximate values that happen to be close but wrong. If a citation were off by <1%, it would be accidental (a typo or copy-paste error), and the likelihood of a typo producing a value within 1% of the correct value is extremely low.

The team considered an asymmetric tolerance (0.5% upper bound, 2% lower bound) to add hysteresis, but decided against it because:
- The 1% symmetric tolerance has been tested against 200 test cases with zero false positives.
- An asymmetric tolerance would introduce a new tuning parameter that would need to be validated against the same test cases.
- The human review fallback (UNCERTAIN → human review) catches any false positives that do occur, at a cost of 2-4 hours per incident, and the expected frequency is less than 1 in 200 citations.

The tolerance decision is documented in `tools/citation_normalizer.py` under "Floating-Point Tolerance Matching — Symmetric Tolerance Decision" (commit `a3f7c9f1`).

**9. The analysis was repeated on two additional scenes at build 33: a flat-plane scene (zero edges) and a mixed scene (50% flat, 50% textured). On the flat-plane scene, 0% of changed splats were near edges (since there are no edges) — the stale metadata's effect was uniform across the plane, producing a consistent opacity shift rather than edge-specific artifacts. On the mixed scene, 34.2% of changed splats were near edges (compared to 5.3% of all pixels being near edges, ratio 6.5× — consistent with the fractal scene's ratio of 4.8×).**

The scene-dependency analysis (commit `a3f7c9fe`) was conducted at build 33 using two additional scenes:

- **Flat-plane scene**: A single colored plane (RGB 128, 128, 128) viewed head-on at zoom level 3. No edges detected by Sobel filter (threshold 0.3). The stale metadata affected splats uniformly across the plane: 100% of changed splats were in non-edge regions (since there are no edge regions). The CONTAIN impact was 0.2 points (from 2.3 to 2.1), which is much smaller than the fractal scene's 0.8-point impact because the flat-plane scene has no edge detail to degrade. The stale metadata produces a consistent opacity shift that slightly reduces containment but does not introduce visible artifacts on flat surfaces (the opacity shift is uniform and within the human visual system's just-noticeable difference for flat surfaces).

- **Mixed scene**: A scene with a flat gray background (50% of pixels) and a fractal pattern overlay (50% of pixels), created by compositing the flat-plane and the fractal sweep at half opacity. The stale metadata affected 34.2% of changed splats at edges, which is consistent with the fractal scene's edge concentration when adjusted for the lower edge-region pixel coverage (5.3% of pixels near edges in the mixed scene vs 14.1% in the fractal scene). The ratio of changed-splat edge concentration to pixel edge coverage is 34.2% / 5.3% = 6.5×, which is actually higher than the fractal scene's 4.8× ratio, suggesting that stale metadata concentrates at edges even more strongly in scenes with flat regions.

The conclusion for low-frequency scenes: the stale metadata's effect on non-edge splats (585 splats from the fractal scene analysis) is relatively benign — it produces a consistent opacity shift that is perceptually masked by the flat surface. The stale metadata's effect on edge splats is the primary concern, and this effect is consistent across scene types (ratio of 4.8× to 6.5×). The scene-dependency analysis is documented in `docs/LESSONS_LEARNED.md` under "Section 3.3: Infrastructure Before Algorithms — Scene Dependency Analysis" (commit `a3f7c9fe`).
