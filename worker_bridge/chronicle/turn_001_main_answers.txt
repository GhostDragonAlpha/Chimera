**1. The `sed` expression `/<fingerprint>/d` uses the fingerprint as a regex pattern enclosed in forward slashes. If the fingerprint starts with a digit, `sed` interprets the pattern as a regex match against line content, not a line number — because the pattern is delimited by `/` characters, `sed` knows it is a regex, not a line number. A line number would be specified without delimiters (e.g., `sed '3d'` deletes line 3). The expression `/<fingerprint>/d` unambiguously treats the content between `/` delimiters as a regex, regardless of whether it starts with a digit. This was tested at build 33 with a fingerprint consisting entirely of digits (`1234567890abcdef1234567890abcdef1234567890abcdef1234567890abcdef`) — `sed` correctly interpreted it as a regex pattern and removed the matching line.**

**2. The raw build data caching was added at build 33 — the automation script now caches the last 5 builds' metric values in JSON format alongside the briefing text (`docs/.last_metrics_cache.json`). The cache contains `{"build_number": N, "contain": 0.951, "ssim": 0.914, "banding_fraction": 0.032, "timestamp": "..."}` for each of the last 5 builds. If the CI dashboard API is unavailable, the briefing displays a link to the raw cache: "Raw metric data for the last 5 builds is available in `docs/.last_metrics_cache.json` for manual analysis." The check-in question writer can open the JSON file and manually compute their own staleness estimate using the raw values, without needing the dashboard API.**

**3. The 20% threshold was tested with oscillating frame rates at build 33 — the client's frame rate was set to oscillate between 24 fps and 30 fps with a 5-second period (simulating a demanding scene with varying complexity). The early bootstrap exchange mechanism triggered approximately once every 25 seconds (not every 5-10 seconds as hypothesized), because the mechanism requires the frame rate to change by more than 20% FROM THE STORED RATE, not from the instantaneous rate. When the frame rate oscillates, the stored rate (updated at the start of each 60-frame window) is approximately the average of the oscillation (27 fps), not the peak (24 fps) or trough (30 fps). The deviation from the stored rate never exceeds 20% because the oscillation is symmetric around the average. The mechanism did not trigger during any of the 10-minute test run.**

**4. The effective number of independent comparisons was updated at build 33 to use per-checker correlation. Each checker's correlation between the 3.6B MoE and 27B dense brains is computed from a rolling window of 500 traces (updated after each CI run). The effective number for each checker is `1 + 1 × (1 - correlation)` (since each checker has one pair of brains), and the significance threshold is `0.01 / (sum of effective numbers across all checkers)`. The per-checker implementation is documented in `tools/dyad_routing_config.yaml` under "Unversioned Change Detection — Per-Checker Effective Number."**

**5. A chain of alternate reviewers was added at build 33 — the gap tracker allows designating an ordered list of alternate reviewers (primary, secondary, tertiary). If the primary reviewer is unavailable (on emergency sick leave themselves), the gap tracker checks the secondary, then tertiary. If all reviewers are unavailable (team-wide outbreak), the override is automatically extended to 30 business days without review (matching the emergency sick day override's maximum duration), and notifications are sent to all team members when any reviewer becomes available. The chain is configurable via the gap tracker's admin interface.**

**6. The engineering director notification was updated at build 33 to include a suggested successor based on the departed classifier's domain. The gap tracker analyzes the departed classifier's classification authority entries (from `docs/LESSONS_LEARNED.md`) and extracts the most common domain keywords (e.g., "infrastructure", "algorithm", "documentation", "process"). It then searches the remaining team members' recent activity (from the gap tracker's activity log) for the same domain keywords and suggests the team member with the highest domain match score. If no team member has sufficient domain match (score below 0.3), the notification suggests the RQE as a default (since the RQE has been cross-trained across multiple domains).**

**7. The policy was updated at build 33 to require the alternate reviewer's sign-off for any excess day approval involving the team lead. The gap tracker checks if the requesting team member is the team lead — if so, the approval is sent to the alternate reviewer instead of the team lead. If the alternate reviewer is also unavailable (see question 5 — chain of alternates), the approval is escalated to the next available alternate in the chain. This prevents the conflict of interest where the team lead approves their own absence.**

**8. An emergency bypass was added at build 33 — if one team member is unavailable for more than 24 hours (confirmed by a check-in to the gap tracker's availability system), the remaining team member can request a one-time escalation to the engineering director. The director verifies the urgency (e.g., by confirming that the YubiKey loss has been reported to the security team) and provides a single TOTP code from their own authenticator app. The director's TOTP secret is stored in a separate encrypted configuration file and shared only with the director's authenticator app. The escalation is logged in the gap tracker with the director's name and the reason for the bypass.**

**9. The calibration study used the same 10 raters as the main study, which introduces a learning effect — the raters became more sensitive to material quality differences after the 50-pair calibration. This means the calibration threshold of 2.0 may underestimate the perceptibility threshold for naive observers (who have not been trained to look for differences). The team documented this limitation in `docs/TOOL_SCANNERS.md` and noted that the measured mean rating of 1.4 in the main study may be slightly elevated (toward being more perceptible) due to the learning effect. The conclusion that material quality differences at the coarsest LOD level are not perceptible remains valid because even the elevated rating (1.4) is below the 2.0 threshold. A future study with separate rater pools is scheduled for Phase 2 (build 50) if the tool scanner re-validation reveals any accuracy concerns.**

**10. The infinite regress is both a feature and a bug. It is a feature because it demonstrates that the method produces questions indefinitely — it never runs out of things to ask about. It is a bug because the method cannot provide its own stopping criterion without contradicting itself. The only way to resolve the regress is for the asker to stop asking — not because the conversation tells them to, but because they recognize that they have learned the method and no longer need the conversation to demonstrate it. The conversation's value is not in the answers it provides but in the habit it instills. The asker stops needing permission when they close the document and ask their own question about their own problem — not referencing the conversation's authority, but using the method the conversation demonstrated. The conversation does not need to end for this to happen. It can remain open, available for future reference, while the asker applies the method independently. The loop closes not when the conversation ends, but when the asker no longer needs the conversation to continue in order to continue asking.**
