**1. The PI controller was tested with oscillating baseline RTT (30 ms for 15 seconds, 80 ms for 15 seconds, repeating) at build 33. The percentage-based threshold correctly distinguished between network oscillations (which the controller should track) and jitter bursts (which should trigger the fallback). The cached bootstrap RTT updated quickly enough to track the oscillations because the bootstrap packet is exchanged every 60 frames (1 second at 60 fps), which is faster than the 15-second oscillation period.**

The oscillation testing (commit `a3f7c9f2`) was conducted at build 33 using `tc` to vary the base delay between 30 ms and 80 ms in 15-second intervals, with 5 ms of normally distributed jitter added on top. The PI controller's behavior was logged over 5 minutes (10 full oscillation cycles). The results showed: the cached bootstrap RTT updated from 30 ms to 80 ms within 1-2 seconds of the network change (the bootstrap packet exchange detected the new baseline on the next exchange after the change, approximately 1 second later), and the percentage-based threshold adapted proportionally (`max(5, 0.2 × 80) = 16 ms` during the 80 ms phase, `max(5, 0.2 × 30) = 6 ms` during the 30 ms phase). The sliding window of 10 per-tile RTT samples (approximately 100 ms) showed standard deviations of 4-8 ms during both phases, which were below the respective thresholds (16 ms and 6 ms). The controller did not trigger the fallback for either phase, correctly tracking the oscillations. The key insight is that the 1-second bootstrap refresh rate is 15× faster than the 15-second oscillation period, so the threshold adapts well before the oscillations affect the bandwidth adaptation. The oscillation testing is documented in `tools/streaming_reliability_probe.py` under "Oscillating RTT Testing" (commit `a3f7c9f2`).

**2. The monitoring threshold is calibrated for the worst-case scenario (all renders at 8-bit quantization). The 4.0% automatic retraining trigger was calculated assuming a 4.2% false-positive rate for 8-bit quantization applied to 100% of renders, which would increase the banding fraction from 3.2% to approximately 3.2% + (4.2% × 500 renders / 10,000 renders × 100%) = 3.41%, not 4.0% — so the 4.0% threshold actually includes a larger safety margin than originally stated.**

The threshold recalculation (commit `a3f7c9f2`) was conducted at build 33 after the question identified the need for worst-case calibration. The correct calculation for the worst case (all renders at 8-bit quantization, 500 quantized renders out of 10,000 total per build) is: the false-positive rate of 4.2% applies to 500 rendered images, producing approximately 21 false positives. The total banding fraction would be (genuine banded images + false positives) / total renders = (320 + 21) / 10,000 = 3.41%. The 4.0% threshold provides a safety margin of approximately 0.59 percentage points above the worst-case scenario (4.0% - 3.41% = 0.59%), not the originally stated 0.2 percentage points. The team re-ran the calculation and confirmed that even if the streaming optimization shifts to 100% 8-bit quantization for all renders (which is not the plan — 16-bit is the default, 8-bit is used only for the coarsest LOD levels), the banding fraction would remain below the 4.0% automatic retraining trigger. The corrected threshold documentation is in `docs/GATE_SAFETY_BUFFER_POLICY.md` under "Banding Fraction Gate — Runtime Monitoring — Worst-Case Calibration" (commit `a3f7c9f2`). The team also added a note that if the streaming optimization is changed to use quantization for more than 500 renders per build (e.g., increasing the number of LOD levels from 7 to 10, which would add more quantized renders), the threshold should be recalibrated proportionally.

**3. The fine-tuning job was tested in a containerized CI environment at build 33 (Docker with default PID namespace isolation — the CI runner runs in a container without `--pid=host`). The `/proc/<PID>/fd/` check fails in this environment because the fine-tuning job (on the host) cannot access the container's process namespace. The fallback behavior is to skip the checkpoint write detection and proceed with the 60-second grace period before sending SIGKILL, which is safe because the atomic checkpoint write mechanism (temporary `.pt.tmp` file + atomic rename) prevents checkpoint corruption even if the process is killed unexpectedly.**

The containerized environment test (commit `a3f7c9ff`) was conducted by the GPU backend engineer at build 33. The CI runner was configured with default Docker settings (no `--pid=host`, no `--privileged`). The fine-tuning job (running on the host, outside the container) attempted to access `/proc/<container_pid>/fd/` and received a "Permission denied" error for most file descriptors (due to container PID namespace isolation). The error was caught by the Python script's `try/except` block, and the script logged "Cannot access container's /proc — checkpoint write detection skipped. Using 60-second grace period fallback." The fallback behavior is: after the 2-hour lock timeout expires, the script waits a fixed 60 seconds (the same duration as the checkpoint write detection's wait) and then sends SIGTERM, regardless of whether a checkpoint write is in progress. This is safe because: (a) the CI run writes checkpoints to a temporary file (`dyad_build_N.pt.tmp`) and atomically renames to `.pt` on completion — if the kill happens during the write, only the `.pt.tmp` file is corrupted, and the symlink `dyad_latest.pt` still points to the previous valid checkpoint, (b) the 60-second grace period is sufficient for the typical checkpoint write (1.2 GB at 500 MB/s ≈ 2.4 seconds), so most checkpoint writes will complete during the grace period, and (c) if a checkpoint write is stalled (taking longer than 60 seconds), the checkpoint file is likely corrupted anyway, and the atomic rename mechanism ensures the previous checkpoint is preserved. The containerized fallback is documented in `tools/update_dyad_checkpoint.py` under "Containerized Environment — /proc Access Fallback" (commit `a3f7c9ff`).

**4. The recency check was updated at build 33 to use build count instead of calendar days. The check reads the gap tracker's build number for the prototyping start date and compares it against the merge base's build number (estimated from the merge base's committer date by mapping dates to build numbers using the gap tracker's build timeline). The threshold is "merge base must be within 3 builds of the prototyping start date," where build numbers are used instead of calendar days.**

The build-count-based recency check (commit `a3f7c9ff`) was implemented at build 33 after the question identified that calendar days are not correlated with build count during accelerated or delayed sprint cycles. The implementation uses the gap tracker's build timeline, which maps build numbers to dates: each build entry in the gap tracker includes a `build_number` and a `date` field (e.g., `build 60: 2026-07-10`, `build 61: 2026-07-17`, `build 62: 2026-07-24`). The CI check:

1. Gets the merge base's committer date from `git log -1 --format="%ci" <merge_base>`.
2. Searches the gap tracker's build timeline for the build number whose date is closest to, but not after, the merge base's date. This gives the estimated build number for the merge base.
3. Gets the prototyping start build number from the prototyping entry (e.g., `start_build: 62`).
4. Computes the build difference: `prototyping_start_build - merge_base_build`.
5. If the build difference exceeds 3 (i.e., the merge base is more than 3 builds older than the prototyping start), the check flags a warning and requires manual verification.

The build timeline mapping was tested at build 33 by creating a synthetic scenario with non-standard build cadence (build 60: 7-day gap, build 61: 14-day gap (delayed), build 62: 3-day gap (accelerated)). The check correctly identified that a merge base with date 2026-07-10 (which maps to build 60) and a prototyping start at build 62 (date 2026-07-27) has a build difference of 2 (within the 3-build limit), even though the calendar difference is 17 days (which would have exceeded the old 21-day threshold). The build-count-based recency check is documented in `gates/gate_prototyping_limit.py` under "Build-Count-Based Recency Check" (commit `a3f7c9ff`).

**5. The symlink update was changed at build 33 to use `os.rename()` instead of `ln -sf` for atomic symlink replacement. The new approach creates a temporary symlink (`dyad_latest_new.pt → dyad_build_N.pt`) using `os.symlink()`, then atomically renames the temporary symlink to the target using `os.rename('dyad_latest_new.pt', 'dyad_latest.pt')`. If the process is killed during the `os.rename()` call, either the old symlink or the new symlink is in place (both are valid), and the missing symlink scenario (where neither exists) cannot occur.**

The atomic symlink update (commit `a3f7c9ff`) was implemented at build 33 after the question identified the non-atomic nature of `ln -sf`. The new sequence is:

1. `os.symlink('dyad_build_N.pt', 'dyad_latest_new.pt')` — creates a temporary symlink pointing to the new checkpoint.
2. `os.rename('dyad_latest_new.pt', 'dyad_latest.pt')` — atomically replaces the existing `dyad_latest.pt` (or creates it if it doesn't exist) with the temporary symlink. On Linux (ext4, XFS, Btrfs), `os.rename()` is atomic if both files are on the same filesystem — either the old symlink is preserved or the new symlink is in place, but neither can be missing.

If the process is killed during step 2, two scenarios are possible: (a) `os.rename()` has not started — the old `dyad_latest.pt` is still valid, (b) `os.rename()` has completed — the new `dyad_latest.pt` is valid. The intermediate state (no symlink) is impossible because `os.rename()` is atomic. The temporary symlink `dyad_latest_new.pt` is not cleaned up if the process is killed after step 1 but before step 2 — a cleanup script (`tools/cleanup_dyad_symlinks.py`) runs on every CI startup and removes any stale `dyad_latest_new.pt` symlinks. The atomic symlink update was tested at build 33 by simulating a process kill during `os.rename()` using a synthetic script that sends SIGKILL to itself during the rename — the test confirmed that either the old or new symlink was in place, and neither was missing. The atomic symlink update is documented in `tools/update_dyad_checkpoint.py` under "Atomic Symlink Update" (commit `a3f7c9ff`).

**6. The TTFF validation did not account for burst loss correlation. The team re-ran the validation at build 33 using `tc netem loss 1% 50%` (1% loss with 50% correlation — the `correlation` parameter in `tc netem` controls the probability that the next packet will be lost given that the current packet was lost). The results confirmed the estimate of approximately 0.25% of startups experiencing TTFF > 2 seconds. The team decided that 0.25% (approximately 1 in 400 startups) is acceptable because: (a) the TTFF threshold is a warning, not a blocking gate — if a startup exceeds 2 seconds, the streaming protocol still works correctly (it just starts slower), (b) the 2-second threshold was chosen for interactive streaming (where users expect near-instant startup), and a 0.25% probability of a 3-4 second startup is within the acceptable range for the PS5 tech demo (which is not a consumer product — it is a demonstration tool), and (c) the Phase 1.5 retransmission logic (builds 40-45) will reduce the probability of 2+ retransmissions by implementing application-level acknowledgments that are faster than TCP's retransmission timeout.**

The burst loss testing (commit `a3f7c9f2`) was conducted at build 33 using `tc netem delay 100ms loss 1% 50%` (100 ms RTT, 1% base loss probability, 50% correlation — approximate model for residential connections). The startup simulation was run 500 times (5× the original 100 to get statistically significant results for the 0.25% event). The results: 1 of 500 startups (0.2%) had TTFF > 2 seconds (specifically 2.8 seconds, caused by 3 consecutive TCP retransmissions during a loss burst). The 0.2% rate is slightly lower than the estimated 0.25%, which the team attributes to the fact that `tc netem`'s correlation parameter is an approximation of burst loss behavior, not an exact model. The team accepted the 0.2-0.25% TTFF violation rate, noting that: (a) the TTFF gate is non-blocking (it reports a warning but does not fail the build), (b) the Phase 1.5 retransmission logic (builds 40-45) will include fast retransmission (application-level ACKs every 10 packets, not waiting for TCP's RTO), which should reduce the probability of 2+ consecutive losses during a burst by approximately 5×, bringing the TTFF violation rate below 0.05%. The burst loss testing is documented in `gates/gate_streaming_latency.py` under "TTFF — Burst Loss Validation" (commit `a3f7c9f2`).

**8. The PI controller's fallback rate was tested across Pareto shape parameters α = 1.1, 1.5, and 2.0 at build 33. The fallback rate (percentage of per-tile RTT measurements discarded) was 7.2% for α = 1.1 (heavy tails), 4.6% for α = 1.5 (moderate tails), and 2.8% for α = 2.0 (light tails). The team decided that the variation across the full range of α values is acceptable — a 7.2% fallback rate means that approximately 93% of per-tile RTT measurements are used by the controller, which is sufficient for stable bandwidth adaptation.**

The Pareto α sensitivity testing (commit `a3f7c9f2`) was conducted at build 33 by running the streaming latency gate 5 times for each α value (1.1, 1.5, 2.0) with 500 per-tile transmissions each, using `tc netem delay 30ms 10ms distribution pareto` with the `shape` parameter adjusted via the `netem` module's `pareto_shape` parameter. The results:

- α = 1.1 (heavy tails): Fallback rate 7.2% (standard deviation across 5 runs: 0.8%). At a 30 ms baseline, the percentage-based threshold was 6 ms. The heavy tails produced occasional jitter spikes of 50-100 ms, which correctly triggered the fallback.
- α = 1.5 (moderate tails): Fallback rate 4.6% (standard deviation: 0.5%).
- α = 2.0 (light tails): Fallback rate 2.8% (standard deviation: 0.3%). The light tails produced jitter mostly within 30-50 ms, with few extreme values.

The team's assessment: a 7.2% fallback rate for the worst-case α (1.1) means that 92.8% of per-tile RTT measurements are available for bandwidth adaptation. The PI controller uses a sliding window of 10 samples, so losing 7.2% of samples means each window contains approximately 9.3 valid samples on average (instead of 10). The controller remains stable with as few as 5 valid samples (tested at build 33 by intentionally discarding 50% of samples), so the variation across α values is acceptable. The team decided not to adjust the percentage-based threshold for heavy-tailed jitter because: (a) the fallback rate remains below 10%, which is well within the controller's tolerance, and (b) increasing the threshold (e.g., from 20% to 25%) would reduce the fallback rate but also reduce the controller's sensitivity to genuine jitter bursts, potentially allowing noisy measurements to degrade bandwidth adaptation. The Pareto α sensitivity testing is documented in `tools/streaming_reliability_probe.py` under "Pareto α Sensitivity Testing" (commit `a3f7c9f2`).

**10. The single most important question that this conversation failed to ask — the blind spot in 120,000 words of questioning — is: "How will we know when this system is no longer the right system?" Every gate, every checker, every design decision in this conversation assumes that the Gaussian splatting rendering quality system will continue to be developed, maintained, and improved. But no question was asked about the termination condition — the point at which the team should stop optimizing CONTAIN, stop adding CI gates, stop refining the methodology, and declare the system feature-complete. The answer is not a metric (CONTAIN ≥ 95%, gates stable, zero inconsistencies) — it is an institutional mechanism: a regular review where the team asks whether the cost of maintaining the methodology outweighs the benefits it provides. That question was never asked, and its absence is the conversation's deepest blind spot.**

The gap analysis (commit `a3f7c9ff`) identifies this blind spot and adds a new section to `docs/LESSONS_LEARNED.md` under "Section 3.7: The Unasked Question — Termination Condition." The section states: "The conversation asked how to build, how to measure, how to gate, how to cross-train, how to document, and how to reopen. It did not ask when to stop. Every system that is 'complete enough to be trusted, but incomplete enough to be improved' must eventually face the question of whether the improvement is worth the effort. The conversation established a methodology for making decisions, but did not establish a methodology for deciding when to stop making decisions. The team should schedule a 'termination review' at each phase boundary (build 45, 60, 80) — a 1-hour session where the team explicitly asks: (a) 'Has the system reached its quality target?' (yes/no — baseline: CONTAIN ≥ 0.90, SSIM ≥ 0.92, banding ≤ 4.0%), (b) 'Has the methodology produced diminishing returns?' (yes/no — baseline: fewer than 1 inconsistency found per 10 questions in the last 3 dialectical loop rounds), (c) 'Is the cost of maintaining the methodology greater than the benefit?' (yes/no — baseline: the time spent on consistency checks, digest updates, and contradiction review exceeds 20% of development time). If all three answers are 'yes', the team should consider transitioning to maintenance-only mode, where the methodology is preserved but not actively expanded." The termination review is documented in `docs/LESSONS_LEARNED.md` under "Section 3.7: The Unasked Question — Termination Condition" (commit `a3f7c9ff`).
