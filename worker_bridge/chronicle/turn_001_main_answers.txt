**5. The compression ratio optimization search has not been run with both TCP and UDP overhead models. The claim of transport-agnosticism is a theoretical assertion based on the optimization's objective function (minimize GPU memory subject to quality constraints), which does not include transport overhead. The team acknowledges that the claim should be empirically verified before the UDP fallback is deployed in Phase 1.5 (builds 40-45).**

The gap analysis (commit `a3f7c9f2`) acknowledges that the transport-agnosticism claim was not empirically validated. The analysis states: "The compression ratio optimization minimizes GPU memory usage subject to SSIM-on-flat-patches ≥ 0.89 and CONTAIN ≥ 0.855. It does not include transport overhead in its objective function. The claim that the optimal compression ratio is the same for TCP and UDP is a theoretical assertion based on the assumption that transport overhead is independent of compression ratio — which is true for the payload data (the compressed LOD meshes are the same regardless of transport), but not necessarily true for the packet count (finer-grained LODs create more packets, which have different overhead characteristics on TCP vs UDP). This assumption has not been empirically verified. The team recommends running the optimization search with both TCP and UDP overhead models during Phase 1.5 (builds 40-45) before the UDP fallback is deployed." The verification plan (Phase 1.5, builds 40-45) includes: (a) implementing a UDP overhead model that accounts for per-packet header overhead and acknowledgment costs, (b) running the compression ratio optimization search with both TCP and UDP objective functions, and (c) comparing the optimal parameters — if they differ by more than 10% in any compression parameter, the claim is rejected and transport-specific optimization is required. The verification plan is documented in `docs/ROADMAP.md` under "Phase 1.5 — Transport Overhead Model Verification" (commit `a3f7c9f2`). The team decided not to block Phase 1 optimization (build 36) on this verification because: (a) the UDP fallback is not deployed until Phase 1.5, (b) the TCP-optimized parameters will work correctly for the TCP streaming — they may not be optimal for UDP, but they will work (the UDP fallback will use the same parameters and produce correct output, just potentially with higher overhead than optimally tuned parameters), and (c) the optimization search is designed to be re-run with different parameters, so retuning at Phase 1.5 is a 1-2 build cost, not a fundamental redesign.

**6. The date verification check was updated at build 33 to also compare the author date against the committer date — if the author date is more than 7 days before the committer date, the check flags an inconsistency and requires manual verification by the tech lead. Additionally, the check compares the committer date of the prototyping branch's first commit against the build timeline, using the committer date (which cannot be backdated with `--date`).**

The enhanced date verification (commit `a3f7c9ff`) was added at build 33 in response to the identified circumvention vector. The check now performs three validations:

1. **Author date vs committer date**: `git log --format="%ai %ci" <branch> | head -1` extracts both the author date and the committer date for the first commit on the prototyping branch. If the author date is more than 7 days before the committer date, the check prints a warning: "Author date (%ai) is significantly before committer date (%ci). This may indicate backdating. Manual verification by tech lead required." The 7-day threshold was chosen because it accounts for legitimate time off (a developer may author commits on a Friday and not push until the following Monday — a 3-day gap) while flagging suspicious gaps (a gap of more than 7 days suggests active backdating).

2. **Committer date vs build timeline**: The check uses the committer date (not the author date) for the primary validation against the build timeline. Since the committer date cannot be backdated with `git commit --date` (it is set by git when `git commit` or `git push` is performed), the check uses `git log --format="%ci" --before=<build_start_date> origin/main | head -1` to verify that the committer date of the first commit on main is before the declared prototyping start date. This is less precise than using the author date (because the committer date reflects when the branch was pushed, not when the work was done), but it is resistant to backdating — a developer cannot fake the committer date.

3. **Cross-validation against the build timer**: The gap tracker also records the build number at which the prototyping entry was created (e.g., `created_at_build: 63`). The CI check verifies that the prototyping start date is before the entry creation date: if the start date is after the creation date, the check fails (the prototyping cannot have started before the entry was created). This prevents a developer from creating the entry after the fact and backdating the start date to before the entry was created.

The enhanced verification was tested at build 33 with a synthetic backdating scenario (simulated using `git commit --date` to set the author date 10 days before the committer date). The check correctly flagged the inconsistency and required manual verification. The enhanced verification is documented in `gates/gate_prototyping_limit.py` under "Backdating Detection" (commit `a3f7c9ff`).

**7. The per-tile RTT measurement latency was characterized at build 33 using the build 32 LOD transition test combined with the build 33 bootstrap packet protocol. The measurements show that per-tile RTT measurements have a standard deviation of 3.2 ms (bootstrap packet: 1.8 ms), which is within the 5 ms threshold considered noisy. The bandwidth adaptation PI controller has a built-in fallback: if the per-tile RTT measurement's standard deviation exceeds 5 ms over a 10-sample window, the controller uses a cached RTT value from the last bootstrap packet measurement instead.**

The RTT characterization (commit `a3f7c9f2`) was conducted at build 33 by running the streaming latency gate with both the bootstrap packet (192 KB, 100 iterations) and the per-tile LOD transmission (average 16 KB, 500 iterations — one per tile across multiple zoom levels). The results:

- **Bootstrap packet**: Average RTT = 14.8 ms, standard deviation = 1.8 ms, range = 11.2-19.4 ms.
- **Per-tile transmission**: Average RTT = 2.1 ms, standard deviation = 3.2 ms, range = 0.8-18.7 ms.

The per-tile RTT's higher standard deviation (3.2 ms vs 1.8 ms) and wider range (0.8-18.7 ms vs 11.2-19.4 ms) are expected because the per-tile transmissions are much smaller (16 KB vs 192 KB), so the transmission time is dominated by network latency rather than transfer time. Small variations in network latency (which are a smaller fraction of the bootstrap packet's 15 ms TTFF) become a larger fraction of the per-tile packet's 2 ms TTFF. The 3.2 ms standard deviation is below the 5 ms threshold that the team considers noisy.

The bandwidth adaptation PI controller's fallback mechanism is: the controller maintains a sliding window of the last 10 RTT measurements (from both bootstrap and per-tile packets). If the standard deviation of the window exceeds 5 ms, the controller discards the latest per-tile measurement and uses the last known good RTT value (the most recent measurement that was within the 5 ms threshold). If no measurements have been valid within the last 10 samples, the controller uses the cached bootstrap RTT (which is updated on every bootstrap packet exchange — approximately every 60 frames). The fallback mechanism was tested at build 33 by injecting synthetic RTT spikes (simulated network congestion causing a 50 ms RTT for a single per-tile packet) — the controller correctly rejected the spike and continued using the previous valid RTT. The RTT characterization and fallback are documented in `tools/streaming_reliability_probe.py` under "RTT Measurement Characterization" (commit `a3f7c9f2`).

**8. The streaming protocol uses blocking sockets with a configurable timeout (set to 5 seconds — well below the latency gate's 100 ms threshold for individual transmissions, but a safety net in case of catastrophic network failure). The `send_all()` loop can block for up to 5 seconds before raising a `socket.timeout` exception, which is caught by the streaming protocol and triggers a connection reset (the server closes the connection and the client retries). The streaming protocol was tested at build 33 with a congested network scenario (simulated using `tc` to add 200 ms of delay and 50% packet loss on the receiver's side) — the sender's `send_all()` loop blocked for an average of 1.2 seconds (not 5 seconds) before the TCP buffer was consumed, and the bootstrap packet was successfully transmitted within the 100 ms threshold for 92% of packets (8% of packets exceeded 100 ms due to TCP retransmissions caused by the simulated loss).**

The socket configuration (commit `a3f7c9f2`) addresses the blocking behavior. The streaming protocol uses blocking sockets with a timeout set by `sock.settimeout(5.0)` (5 seconds). This timeout is a safety net for catastrophic network failure — under normal conditions, even a congested network should not cause a 5-second block for a 192 KB packet. The latency gate's 100 ms threshold is measured end-to-end (server send to client render), not just socket send time — the 5-second socket timeout is only relevant if the TCP buffer is completely full and the receiver is not consuming data, which would indicate a catastrophic failure (receiver crash, network partition). In that case, the 5-second timeout is desirable because it allows the streaming protocol to detect the failure and retry (the server closes the connection, the client reconnects, and the bootstrap packet is re-transmitted). The congestion test at build 33 used `tc` with 200 ms delay and 50% packet loss — this is an extremely congested network (50% loss is near-total failure). Under these conditions, the `send_all()` loop blocked for 1.2 seconds (not 5 seconds) because TCP's built-in retransmission and congestion avoidance mechanisms consumed the available buffer space gradually, not all at once. The bootstrap packet was successfully transmitted within 100 ms for 92% of packets — the 8% that exceeded 100 ms had a median excess of 45 ms (range 101-187 ms). The latency gate measures average latency (not maximum), so the 8% of packets exceeding 100 ms did not cause the gate to fail (the average was 87 ms, below the 100 ms threshold). The socket configuration and test results are documented in `docs/ROADMAP.md` under "Streaming Protocol — Socket Configuration and Congestion Testing" (commit `a3f7c9f2`).

**10. The mechanism for triggering a new conversation cycle is defined in `docs/CONVERSATION_SATURATION.md` under "Phase Boundary Reopening." When a Phase 1 decision contradicts a settled conversation decision, the gap tracker automatically creates a "CONTRADICTION" entry, which triggers a notification to all team members. If any team member responds within 48 hours that the contradiction requires a new Q&A cycle, the conversation is reopened and the saturation status is revoked.**

The reopening mechanism (commit `a3f7c9ff`) is documented in `docs/CONVERSATION_SATURATION.md` and works as follows:

1. **Automatic contradiction detection**: When a new design decision is added to the gap tracker (Phase 1, Phase 2, or Phase 3 decisions), the gap tracker's `check_contradiction()` method compares the new decision's "Rationale" field against the conversation digest's decision log. It uses keyword matching (searching for phrases like "overrides", "contradicts", "revises") and a semantic similarity check (using the Dyad's 3.6B MoE brain, threshold ≥ 0.85) to detect potential contradictions with settled decisions. If a contradiction is detected, the gap tracker creates a "CONTRADICTION" entry with the status "pending_review."

2. **Team notification**: The gap tracker sends a notification to the team's Slack channel (#design-decisions) with the format: "Potential contradiction detected: Phase 1 decision 'Streaming Protocol Degraded Network Gate' (build 33) may contradict settled decision 'Infrastructure Before Algorithms — Exception Process' (turn_009_main_answers, answer 3). The exception process requires infrastructure-first development after prototyping, but the degraded-network gate was implemented before the streaming protocol was fully optimized. Review required within 48 hours."

3. **Reopening vote**: If any team member (engineer or contractor who has been following the conversation) responds to the notification within 48 hours that the contradiction requires a new Q&A cycle, the saturation status is revoked, the conversation is reopened, and a new round of Q&A begins. If no team member responds within 48 hours, the contradiction is marked as "resolved — no new cycle required" and the saturation status is maintained.

4. **Manual reopening**: Any team member can also manually reopen the conversation by creating a "REOPEN" request in the gap tracker, which triggers the same 48-hour notification and vote process. Manual reopening is intended for cases where the automatic contradiction detection missed a contradiction (e.g., because the new decision uses different phrasing than the settled decision).

The reopening mechanism ensures that the conversation is not permanently closed — it can be reopened when new information contradicts settled decisions, but only when at least one team member agrees that the contradiction is significant enough to warrant a new Q&A cycle. The mechanism is designed to balance the need for stability (settled decisions should not be revisited without cause) with the need for adaptability (new information should be able to challenge settled decisions). The reopening mechanism is documented in `docs/CONVERSATION_SATURATION.md` under "Phase Boundary Reopening" (commit `a3f7c9ff`). The team tested the mechanism at build 33 by creating a synthetic contradiction entry and verifying that the notification was sent and the 48-hour timer was started.
