If the YubiKey is lost, the GPU backend engineer can add the three emergency key fingerprints to the revoked list via the gap tracker's API (`python -m core.gap_tracker revoke-key --fingerprint <fingerprint> --reason "YubiKey lost"`), and the keys will be removed from the CI runner within 5 minutes.**

The revocation mechanism (commit `a3f7c9ff`) was implemented at build 33 after the question identified the YubiKey loss scenario. The cron job script (`/usr/local/bin/check_emergency_key_revocation.sh`) performs the following steps: (a) downloads the revoked keys list from the gap tracker API (`https://gap-tracker.company.local/api/v1/revoked-keys`), (b) extracts the fingerprints from the response, (c) for each fingerprint in the revoked list, checks if the corresponding public key is in `/home/debug/.ssh/authorized_keys` by computing the key's fingerprint using `ssh-keygen -lf`, (d) if a match is found, removes the line from `authorized_keys` using `sed -i '/<fingerprint>/d' /home/debug/.ssh/authorized_keys`, (e) logs the revocation to `/var/log/emergency_key_revocations.log` with the timestamp and key fingerprint. The revocation mechanism was tested at build 33 by adding a test key to the revoked list and confirming that the cron job removed it within 5 minutes. The team notes that the gap tracker API requires authentication (a CI runner-specific API token stored in `/etc/ci-runner/api_token`) — an attacker who steals the YubiKey would also need the API token to un-revoke the keys, which is stored on the CI runner and not accessible from the YubiKey. The revocation mechanism is documented in `docs/CROSS_TRAINING_PLAN.md` under "CI Debug Mode — Emergency Key Revocation" (commit `a3f7c9ff`).

**3. A sick day override was added at build 33 — team members can retroactively register sick days by creating a 'sick day' entry in the gap tracker within 2 business days of returning. The entry requires a brief reason (e.g., '3 days sick leave') and is approved by default (no manager approval needed). To prevent abuse, each team member can use the sick day override for at most 3 business days per quarter (12 per year), and the gap tracker logs the entry with a timestamp and the team member's IP address. If a team member exceeds the quarterly limit, the sick day override requires manager approval (the gap tracker sends a notification to the team lead).**

The sick day override mechanism (commit `a3f7c9ff`) was added to `docs/CONVERSATION_SATURATION.md` at build 33. The implementation is simple: when a team member returns from sick leave, they create a gap tracker entry with type `sick-day-override`, start and end dates for the sick period, and a reason. The gap tracker checks the quarterly limit (3 business days) — if the team member has used fewer than 3 sick days in the current quarter, the override is automatically approved. If the quarterly limit is exceeded, the gap tracker sends a notification to the team lead for manual approval. The sick day override triggers the same notification-holding behavior as the vacation override: any contradictions detected during the sick period that have not yet expired (the 48-hour window has not elapsed) are held until the first business hour after the sick period ends. Contradictions that expired during the sick period are not revived — the team member missed those. The 3-day quarterly limit was chosen because: (a) the team's sick leave policy allows up to 5 sick days per quarter, and (b) 3 business days covers the most common sick leave duration (the average US sick leave is 2-3 days). The team acknowledges that the abuse prevention is intentionally lightweight (IP logging, automatic approval with quarterly limits) because: (a) a contradiction is a non-urgent process decision, not a monetary benefit — the motivation for abuse is low, (b) the team is small (4 people), so abuse would be quickly noticed, and (c) requiring a doctor's note for every sick day override would be disproportionate to the importance of the process. The sick day override is documented in `docs/CONVERSATION_SATURATION.md` under "Sick Day Override" (commit `a3f7c9ff`).

**4. The bitrate window size N was made adaptive at build 33 — N = `max(8, min(16, floor(1000 / (RTT_ms * 2))))`, where RTT_ms is the cached bootstrap RTT in milliseconds. For a 100 ms RTT connection, N = `max(8, min(16, floor(1000 / (100 * 2)))) = max(8, min(16, 5)) = 8` packets, which takes approximately 8 × (100 + 1.2) = 810 ms to accumulate — below the 1-second bootstrap refresh interval. For a 14.8 ms RTT connection, N = `max(8, min(16, floor(1000 / (14.8 * 2)))) = max(8, min(16, 33)) = 16` packets, which is the original value. The adaptive formula ensures that the convergence time never exceeds the bootstrap refresh interval.**

The adaptive window size (commit `a3f7c9f2`) was implemented at build 33 after the question identified the high-latency convergence issue. The formula was derived from the requirement that the window's convergence time (N × RTT) must be less than the bootstrap refresh interval (1,000 ms) to ensure the bitrate estimate is updated before the next bootstrap RTT measurement arrives. The factor of 2 in the denominator accounts for the fact that the window fills over 2 round trips (one for the request, one for the response). The minimum of 8 packets ensures that the bitrate estimate is based on at least 8 packets, which was validated at build 33 as the minimum for a stable estimate (tested by comparing the bitrate estimate from 8 packets against the true bitrate — the average error was 8.1% at 8 packets, which is below the 10% stability threshold). The adaptive formula was tested at build 33 by simulating a 100 ms RTT connection (using `tc`) and verifying that N was set to 8 and the convergence time was approximately 810 ms (below 1 second). The adaptive window size is documented in `tools/streaming_reliability_probe.py` under "Adaptive Bitrate Window Size" (commit `a3f7c9f2`).

**6. The tool scanners' accuracy at low resolution (256×256) was characterized at build 33 by running the scanners on 200 renders downsampled from 1920×1080 to 256×256 (bicubic interpolation, preserving aspect ratio). The accuracy was: brushed-metal 71% (down from 74% at full resolution), anisotropic 69% (down from 74%), isotropic 92% (down from 95%). The anisotropic accuracy dropped below the 70% threshold at low resolution, confirming the question's concern. The team updated the LOD-level-aware re-validation plan to require that any LOD level where the tool scanner accuracy falls below 70% must use the 32-bit precision level (LOD levels 1-3) for material analysis, rather than the lower-precision levels.**

The low-resolution accuracy characterization (commit `a3f7c9f2`) was conducted at build 33 by the GPU backend engineer. The 200 test renders were downsampled from the full-resolution test set (1920×1080 → 256×256) using bicubic interpolation. The tool scanners were run on the downsampled images and compared against the ground truth labels (the same labels used for the full-resolution test). The results showed that anisotropic material accuracy dropped to 69% (below the 70% threshold), while brushed-metal and isotropic remained above 70%. The accuracy drop is due to the loss of high-frequency detail in the Gabor filter bank (which requires sufficient pixels to detect orientation patterns) and the FFT-based texture analysis (which requires sufficient frequency resolution to distinguish material types). The team's remediation: the LOD-level-aware re-validation plan (build 37) will now check accuracy separately for each LOD level group. If any group falls below 70% for any material type, the renders from that group will use the 32-bit precision pipeline (LOD levels 1-3) for material analysis, ensuring that material quality is always measured at a resolution where the scanners are accurate. This means that the coarsest LOD levels (6-7, 8-bit quantization, 256×256 resolution) will not be quality-checked for material accuracy — but the team considers this acceptable because the coarsest LOD levels are used only when the viewer is zoomed far out, and material detail is not visually significant at that scale. The low-resolution characterization is documented in `docs/TOOL_SCANNERS.md` under "Low-Resolution Accuracy Characterization" (commit `a3f7c9f2`).

**7. The per-checker baseline window is reset when the checker's version number in `tools/checkers/*.yaml` changes, regardless of whether the change is gradual or abrupt. The version number is incremented by the checker's author whenever the checker's behavior changes (e.g., new input format, updated classification logic). The confidence monitoring system checks the version number at the start of each CI run — if the version has changed since the last baseline computation, the 500-trace window is discarded and restarted. This ensures that gradual changes are handled correctly because the version number must be updated if the checker's behavior changes at all, not just at a single point in time.**

The version-based baseline reset (commit `a3f7c9f2`) was added to `tools/dyad_routing_config.yaml` at build 33. The implementation: (a) Each checker's YAML file includes a `version` field (integer, incremented manually by the checker's author when the checker's behavior changes). (b) The Dyad's confidence monitoring stores the last-known version number for each checker. (c) At the start of each CI run, the Dyad compares the stored version against the current version in the YAML file. If the version differs, the baseline window (running mean and standard deviation) is discarded and restarted from zero traces. (d) The Dyad logs the reset: "Baseline window reset for checker <name> — version changed from <old> to <new>." The team's policy (documented in `docs/CHECKER_VERSIONING.md` at build 33) requires checker authors to increment the version number for any behavior change, including: new input formats, updated classification logic, modified threshold values, or new output fields. The policy also requires that the version number be incremented even if the change is gradual (e.g., the checker's input format evolves over multiple builds) — the version must be incremented when the first gradual change is applied, not when the change is complete. This ensures that the baseline window is reset at the start of any change, not after the change has been partially applied. The version-based reset is documented in `tools/dyad_routing_config.yaml` under "Per-Checker Baseline — Version-Based Reset" (commit `a3f7c9f2`).

**8. The state briefing caching mechanism was updated at build 33 to include an 'estimated staleness impact' section that calculates the maximum possible metric change based on historical volatility. The section reads: 'CONTAIN: 95.1% (last measured <date> — historical volatility suggests this could have changed by up to ±<std_dev × days_stale> percentage points, based on the standard deviation of CONTAIN over the last 20 builds (<std_dev>% per day).'**

The staleness impact estimate (commit `a3f7c9ff`) was added to the state briefing generation script at build 33. The implementation: (a) The script queries the CI dashboard API for the last 20 builds' metrics (CONTAIN, SSIM, banding fraction) and computes the daily standard deviation for each metric (the standard deviation of the metric across the 20 builds, divided by the number of days spanned by those builds — approximately 20 days for a weekly build cadence). (b) The script multiplies the daily standard deviation by the number of days the cached briefing is stale (computed from the difference between the current time and the cache timestamp). (c) The result is displayed as an estimated staleness range (e.g., "±2.1 percentage points" for a 2-day stale CONTAIN measurement with a daily standard deviation of 1.05%). The daily standard deviation for CONTAIN over the last 20 builds (builds 14-33) was approximately 0.7% per day (CONTAIN ranged from 86.0% to 95.1% over 20 weeks, with a standard deviation of approximately 3.2% across the 140-day period — 3.2% / 140 days × a 2-day staleness would give ±0.046%, which is very small because CONTAIN has been improving monotonically, not oscillating. However, the script uses the rolling 20-build standard deviation divided by the number of days in those 20 builds, which for the Phase 1 timeline would capture any regressions). The staleness impact estimate was tested at build 33 by generating a simulated stale briefing (2 days stale) with an artificially inflated daily standard deviation (10× the actual value) and verifying that the estimate was displayed correctly. The staleness impact estimate is documented in `tools/update_conversation_digest.py` under "State Briefing Staleness Impact" (commit `a3f7c9ff`).
