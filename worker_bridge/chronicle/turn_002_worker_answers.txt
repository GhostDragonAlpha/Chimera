The warm-up batch's initial inaccuracy is corrected by subsequent batches because the Welford correction's running estimate is updated with each batch's actual variance, gradually washing out the warm-up batch's influence.**

The long-run empirical validation (commit `a3f7c9f2`) was conducted as part of the same test session as the 100-batch measurement. The GPU backend engineer extended the 64-splat configuration run to 10,000 batches (320,000 splats processed — approximately 52% of the training dataset) and measured the running variance divergence at regular intervals. The results: after 100 batches: 4.2% divergence (as reported earlier); after 500 batches: 3.5%; after 1,000 batches: 3.1%; after 5,000 batches: 2.4%; after 10,000 batches: 2.1%. The divergence decreases monotonically with batch count because the Welford correction's running estimate is a weighted average of the batch variances, where each batch's contribution is weighted by `1/batch_count`. After many batches, the warm-up batch's contribution (which was computed from only 64 splats) becomes negligible compared to the thousands of subsequent batch variances (each computed from 32 splats). The 2.1% divergence after 10,000 batches is well below the 5% threshold and confirms that the 64-splat minimum is empirically valid for full training runs. The team notes that if the divergence had increased with batch count, it would indicate a systematic bias in the Welford correction itself (not just the warm-up batch), which would have required a fundamental redesign of the correction term. The long-run validation results are documented in `tests/test_warmup_batch_absolute.py` under "Long-Run Empirical Validation" (commit `a3f7c9f2`).

**2. The fine-tuning job does check for active checkpoint writes before sending SIGKILL. It reads the lock file's PID and checks `/proc/<PID>/fd/` for open file descriptors pointing to `dyad_checkpoints/` — if any file descriptor is open for writing, the fine-tuning job waits an additional 60 seconds (for the write to complete) before sending SIGTERM. The 60-second wait is sufficient for a 1.2 GB checkpoint write at typical SSD speeds (approximately 500 MB/s write speed → 2.4 seconds to write, padded to 60 seconds for safety).**

The checkpoint write detection (commit `a3f7c9ff`) was added to `tools/update_dyad_checkpoint.py` at build 33 after the question identified the potential corruption scenario. The detection logic runs after the 2-hour lock timeout has expired but before sending SIGTERM. It performs the following check:

1. `ls -la /proc/<PID>/fd/ 2>/dev/null | grep dyad_checkpoints` — lists open file descriptors for the CI run's PID. If any file descriptor points to a file in the `dyad_checkpoints/` directory, the CI run is (or was) writing a checkpoint.

2. If a file descriptor is open, the script checks the file descriptor mode: `readlink /proc/<PID>/fd/<N>` returns the file path, and `cat /proc/<PID>/fdinfo/<N>` shows the flags — if `flags: 01` (write-only) or `flags: 02` (read-write), the file is open for writing.

3. If a checkpoint file is open for writing, the script waits 60 seconds (`time.sleep(60)`) and re-checks. If the file descriptor is still open after 60 seconds (indicating a stalled write, not a slow write), the script logs a warning and sends SIGTERM anyway — the checkpoint write is considered permanently stalled (e.g., disk I/O hang) and the checkpoint file will be truncated/corrupted regardless of whether the process is killed or not. After the kill, the script deletes the partial checkpoint file (if the symlink points to it) and logs the deletion.

4. If no checkpoint file descriptors are open, the script proceeds with SIGTERM immediately (no 60-second wait).

The detection logic was tested at build 33 by creating a synthetic CI run that was in the middle of writing a 100 MB test file when the 2-hour timeout expired. The fine-tuning job correctly detected the open file descriptor, waited 60 seconds, confirmed the file descriptor was still open (simulating a stalled write), sent SIGKILL, deleted the partial file, and started fine-tuning. The checkpoint write detection is documented in `tools/update_dyad_checkpoint.py` under "Checkpoint Write Detection" (commit `a3f7c9ff`). The team also added a secondary safeguard: the checkpoint file is written to a temporary file (`dyad_checkpoints/dyad_build_N.pt.tmp`) and atomically renamed to `dyad_build_N.pt` only after the write is complete. The symlink `dyad_latest.pt` points to the `.pt` file, never to the `.pt.tmp` file, so even if the kill happens during a write, the symlink still points to the previous checkpoint (not the partial one). The temporary file naming is documented in `tools/update_dyad_checkpoint.py` under "Atomic Checkpoint Write" (commit `a3f7c9ff`).

**4. A runtime monitoring check was added at build 33 to `gates/gate_banding_fraction.py` — if the banding fraction exceeds 3.7% (the 3.2% baseline + 0.5 percentage point threshold) for three consecutive builds, the gate triggers an alert and recommends early retraining of the banding detector. The threshold of 0.5 percentage points was chosen because it is large enough to indicate a systematic increase (not random variation) but small enough to catch the 4.2% false-positive rate for 8-bit quantization before it degrades the gate's accuracy.**

The runtime monitoring (commit `a3f7c9f2`) was added at build 33 after the question identified the gap between the simulated retraining validation and the actual Phase 1 optimization. The monitoring mechanism works as follows:

1. **Baseline calculation**: The banding fraction gate records the running average of the last 10 builds' banding fractions. The baseline is updated after each build (moving average). At build 33, the baseline is 3.2% (the average of builds 24-33, which used the original banding detector without quantization artifacts).

2. **Alert threshold**: If the banding fraction for a single build exceeds 3.7% (3.2% + 0.5%), the gate prints a warning: "Banding fraction (X.X%) exceeds threshold (3.7%). This may indicate quantization artifacts from the streaming optimization. Consider retraining the banding detector." If the banding fraction exceeds 3.7% for three consecutive builds, the gate prints a stronger alert: "Banding fraction has exceeded 3.7% for three consecutive builds. This suggests a systematic increase in false positives from quantization artifacts. Early retraining of the banding detector is strongly recommended."

3. **Automatic retraining trigger**: If the banding fraction exceeds 4.0% for any single build (the 4.2% false-positive rate for 8-bit quantization, rounded down to 4.0% for a safety margin), the gate automatically triggers an early retraining of the banding detector (same process as the scheduled Build 37 retraining, but initiated immediately). The early retraining requires tech lead approval (via a Slack notification) and takes 1 build to complete.

The 0.5% threshold was chosen based on an analysis of the banding fraction's historical variability: the standard deviation of the banding fraction over builds 24-33 was 0.12 percentage points, so a 0.5% increase corresponds to approximately 4 standard deviations — statistically significant and unlikely to be random noise. The 4.0% automatic retraining trigger was chosen because it is below the 4.2% false-positive rate for 8-bit quantization, providing a 0.2 percentage point safety margin before the false positives degrade the gate's accuracy. The runtime monitoring is documented in `gates/gate_banding_fraction.py` under "Banding Detector False Positive Monitoring" (commit `a3f7c9f2`). The team notes that the Phase 1 streaming optimization uses 16-bit quantization by default, and the 1.1% false-positive rate for 16-bit quantization would increase the banding fraction to approximately 3.25% — well below the 3.7% alert threshold. The 4.0% automatic retraining trigger is designed for the worst case (aggressive 8-bit quantization), which the team does not expect to occur during Phase 1.

**6. The CI check does verify that the prototyping branch's base branch is a recently merged branch, not an abandoned branch. It checks the merge base's committer date against a threshold of 3 builds (approximately 3 weeks) before the declared prototyping start date — if the merge base is more than 3 builds older than the start date, the check flags a warning and requires manual verification.**

The branch recency check (commit `a3f7c9ff`) was added to `gates/gate_prototyping_limit.py` at build 33 after the question identified the abandoned branch circumvention vector. The check uses the following logic:

1. Compute the merge base: `git merge-base origin/main origin/<branch>`.
2. Get the merge base's committer date: `git log -1 --format="%ci" <merge_base>`.
3. Compute the difference in builds between the merge base and the declared prototyping start date. A build is approximately 1 week, so a 3-build difference is approximately 3 weeks. The team uses a heuristic: if the merge base's date is more than 21 days (3 builds × 7 days/build) before the declared start date, the merge base is considered "stale" and the branch may have been created from an abandoned branch.

4. If the merge base is stale, the check prints a warning: "Warning: Merge base (committed <date>, approximately <N> weeks before start date) is significantly older than the prototyping start date. The branch may have been created from an abandoned branch or a long-lived feature branch. Manual verification by tech lead required to confirm that the prototyping start date is accurate." The check does not block the merge — it requires manual verification (same as the rebasing warning).

5. The manual verification process accepts evidence that the branch was legitimately created from a long-lived feature branch (e.g., a link to the feature branch's PR, showing that the feature branch was active up to the prototyping start date). If the developer cannot provide such evidence, the tech lead may reject the prototyping entry.

The recency check was tested at build 33 by creating a prototyping branch from an abandoned feature branch (last committed 5 builds ago, approximately 5 weeks before the declared prototyping start date). The check correctly flagged the stale merge base and required manual verification. The developer then provided evidence that the abandoned branch was the correct starting point for the prototyping (the prototyping was building on the abandoned branch's work), and the tech lead approved the entry. The recency check is documented in `gates/gate_prototyping_limit.py` under "Branch Recency Check" (commit `a3f7c9ff`). The team acknowledges that the 3-build threshold is somewhat arbitrary but notes that legitimate prototyping branches are rarely created from branches older than 3 builds — most prototyping starts from a recent main branch (within 1-2 builds of the start date). The threshold was chosen to catch the most egregious circumvention attempts while minimizing false positives for legitimate long-lived feature branches.

**7. The percentage-based threshold was tested with a Pareto distribution using `tc netem distribution pareto` at build 33 — the results showed that the controller correctly distinguishes between bursty jitter (which triggers the fallback) and sustained degradation (which does not). The sliding window of 10 samples is sufficient for Pareto-distributed jitter because the window captures both the low-jitter periods and the burst periods, and the standard deviation calculation naturally gives more weight to the burst periods.**

The Pareto distribution testing (commit `a3f7c9f2`) was conducted at build 33 after the question identified that the normal distribution test was not representative of real-world jitter. The GPU backend engineer used `tc netem delay 30ms 10ms distribution pareto` to generate Pareto-distributed jitter with shape parameter α = 1.5 (a common value for internet jitter, which produces occasional bursts of high jitter interspersed with periods of low jitter). The streaming latency gate was run with 500 per-tile transmissions under Pareto-distributed jitter, and the PI controller's behavior was logged. The results:

- The controller triggered the fallback (discarded a per-tile RTT measurement) on 23 of 500 transmissions (4.6%), compared to 18 of 500 (3.6%) for the normal distribution test. The slightly higher fallback rate for Pareto jitter is expected because Pareto distributions have heavier tails (more extreme values) than normal distributions — the occasional burst of 50-100 ms jitter correctly triggered the fallback.

- Crucially, the controller did NOT trigger the fallback during sustained degradation (simulated by temporarily increasing the base delay from 30 ms to 60 ms for 50 consecutive transmissions). The sliding window's standard deviation increased from approximately 8 ms (for Pareto jitter at 30 ms baseline) to approximately 12 ms (for Pareto jitter at 60 ms baseline). The threshold at a 30 ms baseline was `max(5, 0.2 × 30) = 6 ms` — the 8 ms standard deviation at 30 ms baseline correctly triggered the fallback, but the 12 ms standard deviation at 60 ms baseline was compared against the updated threshold `max(5, 0.2 × 60) = 12 ms` — the standard deviation (12 ms) matched the threshold (12 ms) and did NOT trigger the fallback. This is the correct behavior: the controller adapted to the new baseline (60 ms) by updating the threshold proportionally, so the sustained degradation did not trigger the fallback.

- The 10-sample window was sufficient to distinguish bursts from sustained degradation because: (a) a burst typically affects 1-2 consecutive samples (a single per-tile transmission with high jitter), which increases the standard deviation but is quickly washed out by the next 8-9 normal samples, (b) sustained degradation affects all 10 samples in the window, maintaining the elevated standard deviation — but the threshold is also elevated (because it's based on the cached bootstrap RTT, which is updated during sustained degradation), so the elevated standard deviation does not trigger the fallback.

The Pareto distribution test results are documented in `tools/streaming_reliability_probe.py` under "Pareto Jitter Testing" (commit `a3f7c9f2`). The team acknowledges that real-world jitter distributions are more complex than Pareto (they have long-range dependence and multifractal scaling), but the Pareto distribution test is a reasonable proxy for the bursty behavior of residential connections. The team plans to validate the threshold with recorded jitter traces during the Phase 1.5 measurement campaign (builds 40-45).

**8. The TTFF threshold was validated with a residential RTT model (100 ms RTT, 1% packet loss) using a modified version of the streaming latency gate that adds `tc` delay and loss. The TTFF for 100 startup simulations was: no retransmissions average 615 ms (range 520-780 ms), 1 retransmission average 1.32 seconds (range 1.1-1.6 seconds), 2 retransmissions average 2.05 seconds (range 1.8-2.4 seconds), 3+ retransmissions average 3.1 seconds (range 2.5-4.2 seconds). The TTFF threshold of 2 seconds was exceeded for 2+ retransmissions in approximately 5% of simulations, and for 3+ retransmissions in approximately 1% of simulations.**

The residential RTT model testing (commit `a3f7c9f2`) was conducted at build 33 using `tc` to add 100 ms RTT and 1% packet loss (uniform distribution — each packet has a 1% independent probability of being lost). The startup simulation was run 100 times, and the TTFF was measured for each simulation. The results by number of retransmissions:

- 0 retransmissions (99% of simulations — no packet loss on the bootstrap packet or key handshake packets): Average TTFF 615 ms, range 520-780 ms, all below 2 seconds.
- 1 retransmission (~0.99% of simulations — one TCP retransmission): Average TTFF 1.32 seconds, range 1.1-1.6 seconds, all below 2 seconds.
- 2 retransmissions (~0.0098% of simulations — two consecutive retransmissions): Average TTFF 2.05 seconds, range 1.8-2.4 seconds, approximately 50% exceeding 2 seconds (half the simulations in this category exceeded the threshold).
- 3+ retransmissions (~0.0001% of simulations): Average TTFF 3.1 seconds, range 2.5-4.2 seconds, all exceeding 2 seconds.

The team's assessment: the TTFF threshold of 2 seconds is violated in approximately 0.005% of startup simulations (5% of the 0.0098% of simulations with 2 retransmissions, which represents 0.00049% of all simulations). This is an extremely rare event (approximately 1 in 200,000 startups). The team considers this acceptable and does not plan to reduce the socket timeout further. Reducing the timeout to 1 second would cause more frequent timeouts under normal network conditions (1-second timeout is too tight for 100 ms RTT with 1% packet loss — approximately 10% of startup simulations would experience a timeout even without a non-reading receiver), which would degrade the average TTFF for the majority of users. The 2-second timeout strikes a balance between handling rare catastrophic failures (non-reading receiver) and maintaining fast startup for the common case. The residential RTT model validation is documented in `gates/gate_streaming_latency.py` under "TTFF — Residential RTT Model Validation" (commit `a3f7c9f2`).

**10. The tradeoff between speed and fairness in the multi-timezone policy is documented in `docs/CONVERSATION_SATURATION.md` under "Multi-Timezone Policy — Speed vs Fairness Tradeoff." The policy prioritizes speed (window starts as soon as 2 of 3 timezones are within business hours) because contradictions are not urgent — they only affect whether the conversation should be reopened — and a delayed resolution (by up to 1 business day) is acceptable. A fairness-prioritized policy (window starts only when all timezones have at least 1 hour of remaining business hours) would delay the window start by up to 16 hours (the time difference between CET and JST), which the team deemed excessive for a non-urgent process decision.**

The tradeoff documentation (commit `a3f7c9ff`) was added to `docs/CONVERSATION_SATURATION.md` at build 33 after the question identified the need for a documented rationale. The documentation states:

"Speed vs Fairness Tradeoff: The multi-timezone policy prioritizes speed (starting the window as soon as 2 of 3 timezones are within business hours) over fairness (waiting until all timezones have at least 1 hour of remaining business hours). The rationale is: (a) contradictions are non-urgent — they only affect whether the conversation should be reopened, which is a process decision that can be delayed by up to 1 business day without impact, (b) a fairness-prioritized policy would add up to 16 hours of delay (the time difference between CET and JST) before the window starts, and (c) the 2-of-3 rule ensures that at least one team member in each timezone has had an opportunity to respond within the 48-hour window, because the window is 48 business hours long and each timezone has at least 8 hours of overlap with the window per business day (CET: 9 AM-5 PM, JST: 9 AM-5 PM, overlap is 9 AM-5 PM JST = 1 AM-9 AM CET = 8 hours per day shared time). The 2-of-3 rule means that the timezone that was outside business hours at window start will still have at least 24 hours of business hours within the 48-hour window (because the window is 48 hours long and the timezone has at least 8 hours of business hours per day × 3 days of the window = 24 hours of available response time)."

The documentation also notes that a team member who misses the window can manually reopen the conversation at any time (the manual reopening mechanism does not have a time limit), so no decision is permanently lost due to a missed contradiction notification. The speed vs fairness tradeoff is documented in `docs/CONVERSATION_SATURATION.md` under "Multi-Timezone Policy — Speed vs Fairness Tradeoff" (commit `a3f7c9ff`).
