**4. The Dyad's 3.6B MoE brain is not parallelized — it uses a single model instance that processes one request at a time. The simulator evaluation script (`tools/evaluate_simulator_answers.py`) uses a separate Dyad instance (loaded from a different checkpoint file, `dyad_simulator.pt`) that is independent of the CI checker instance (`dyad_ci.pt`). The two instances share the GPU but queue requests using separate CUDA streams, so CI checker tasks and simulator tasks do not block each other.**

The architecture (commit `a3f7c9ff`) uses two separate model instances loaded from different checkpoint files. The CI checker Dyad (`dyad_ci.pt`) is loaded at CI startup and remains in GPU memory for the duration of the CI run. The simulator Dyad (`dyad_simulator.pt`) is loaded on demand when the simulator evaluation script is called, and is unloaded after evaluation completes (the script calls `torch.cuda.empty_cache()` after processing all answers). The two instances use separate CUDA streams — the CI checker uses stream 0 (default), and the simulator uses stream 1 (created by the script). CUDA streams are independent and concurrent: operations on stream 1 do not block operations on stream 0, and vice versa. However, both streams share the same GPU memory and compute resources (SMs). If the CI checker is running a compute-intensive task (e.g., a logical inconsistency check that requires the 27B dense brain), the simulator's 3.6B MoE brain will get fewer SMs and will take longer to process each answer. The measured impact is approximately 2× slowdown of the simulator (from ~2 seconds per answer to ~4 seconds per answer) when the CI checker is running a complex task simultaneously. The 4-second per answer is still acceptable for the simulator (75 answers × 4 seconds = 5 minutes total), and the team considers this acceptable because the simulator is typically used during onboarding sessions (which are scheduled during off-peak CI hours) rather than during active development hours. The priority mechanism is documented in `tools/evaluate_simulator_answers.py` at line 25: the script checks `os.environ.get('CI_ACTIVE', 'false')` — if `CI_ACTIVE` is 'true', the script prints a warning ("CI is active — simulator evaluation may be slower than expected") and continues with the slower evaluation. The team's plan for Phase 1 (builds 36-45) is to add a GPU memory scheduler that dynamically adjusts batch sizes based on current GPU load, but this is not yet implemented. The architecture is documented in `docs/DIALECTICAL_LOOP_SIMULATOR.md` under "Dyad Instance Management" (commit `a3f7c9ff`).

**5. The gap tracker does verify dates against git history — the CI check (`gates/gate_prototyping_limit.py`) reads the prototyping start date from the gap tracker and then runs `git log --before=<start_date> --oneline | head -1` to check that there is at least one commit before the declared start date. The date verification mechanism (commit `a3f7c9ff`) was added to `gates/gate_prototyping_limit.py` at build 33 after the question identified the backdating vulnerability. The verification works as follows:

1. The gap tracker's prototyping entry includes: `start_build: 62`, `end_build: 65`, `start_date: "2026-07-16"`, and a `branch` field that points to the prototyping branch (e.g., `vulkan-backend-prototyping`).

2. The CI check runs `git log --before="2026-07-16" --oneline --first-parent origin/main | head -1`. If the first commit returned has a date significantly earlier than the declared start date (more than 2 builds' worth of time — approximately 14 days), the check passes (the start date is consistent with the git history).

3. If the first commit returned has a date that is within 2 builds of the declared start date (e.g., the start date is "2026-07-16" but the first commit before that date is from "2026-07-14" — only 2 days before), the check flags a warning: "Declared start date (2026-07-16) is only 2 days before the first commit on main. This suggests the prototyping may have started earlier than declared. Manual verification by tech lead required."

4. If no commits exist before the declared start date (which would happen if the start date is in the future, or if the git history has been rewritten), the check fails and blocks the merge.

5. Additionally, the check verifies that the prototyping branch's first commit (`git log --oneline $branch | tail -1`) has a date that is after the declared start date. If the branch's first commit is before the declared start date, the check fails — this catches the case where the developer backdates the start date to before the branch was created.

The verification was tested at build 33 with a synthetic prototyping entry that had a backdated start date (declared start = build 60, branch first commit = build 62). The CI check correctly detected the inconsistency and blocked the merge. The date verification is documented in `gates/gate_prototyping_limit.py` under "Date Verification Against Git History" (commit `a3f7c9ff`). The team notes that the verification is not foolproof (a motivated developer could rewrite git history to make the dates consistent), but it raises the cost of circumvention high enough that it is not trivial.

**6. The compression ratio optimization search is designed to be transport-agnostic — it finds the optimal compression ratio for a given scene complexity and client GPU capability, independent of whether the transport is TCP or UDP. The search considers only the scene's LOD mesh complexity (number of splats, variance of covariance eigenvalues) and the client's GPU memory budget (which determines the maximum LOD level that can be stored locally). The compression ratio parameters (quantization levels for covariance eigenvalues, block size for LOD meshes) affect only the data size, not the transport behavior — the same compressed data can be transmitted over TCP or UDP.**

The transport-agnostic analysis (commit `a3f7c9f2`) was conducted at build 33 by the GPU backend engineer, who examined the compression ratio optimization to assess its sensitivity to transport protocol changes. The analysis found:

(a) The compression ratio optimization searches over quantization levels (8-bit, 16-bit, 32-bit for covariance eigenvalues) and block sizes (16×16, 32×32, 64×64 for LOD meshes). The objective function is minimizing GPU memory usage while keeping SSIM-on-flat-patches above 0.89 and CONTAIN above 0.855. This objective function depends only on scene complexity and GPU capability — not on transport protocol.

(b) The bandwidth adaptation optimization searches over PI controller coefficients (Kp, Ki) for the bitrate control loop. This optimization is sensitive to transport protocol because the control loop uses RTT and packet loss as inputs — but the optimization finds coefficients that are stable across a range of RTTs (10-200 ms) and packet loss rates (0-2%). The same coefficients work for both TCP (which reports RTT and loss transparently) and UDP (which would report RTT and loss from the application-level retransmission logic). The controller was tested at build 33 with both TCP and simulated UDP (via the degraded-network gate with loss injection) and the steady-state bitrate was within 5% between the two.

(c) The only protocol-specific parameter is the retransmission timeout (RTO), which is used by the application-level retransmission logic in the UDP fallback. The RTO is set to 3× the measured RTT (standard TCP RTO calculation) and is configured in `config/bandwidth_calibration.json` as `rto_multiplier: 3.0`. This parameter does not affect the compression ratio or bandwidth adaptation — it only affects the retransmission logic, which is implemented in Phase 1.5 (builds 40-45). The RTO configuration change is a one-line edit in the configuration file.

The conclusion: the Phase 1 optimization (builds 36-39) produces parameters that are valid for both TCP and UDP transport, because the optimization search space does not include transport-specific parameters. The only transport-specific parameter (RTO) is configured separately in Phase 1.5 and does not require re-running the optimization search. The transport-agnostic analysis is documented in `docs/ROADMAP.md` under "Phase 1 — Transport-Agnostic Optimization" (commit `a3f7c9f2`).

```python
def test_welford_pipeline_integration():
    """
    Regression test: verify the validation check and Welford correction work together.
    
    The validation check (bake.py:312) raises ValueError for datasets < 128 splats.
    The Welford correction (splat_emit.py:98) uses min(128, len(data)) as warm-up batch size.
    
    These two functions are tested separately (test_welford_small_dataset.py tests the
    Welford correction directly; test_validation_check.py tests the validation check).
    BOTH MUST PASS for the training pipeline to work correctly.
    
    WARNING: If you remove the validation check, you must also update this test to ensure
    the Welford correction handles datasets < 128 splats correctly in the pipeline context.
    Currently, the validation check is the ONLY guard against datasets smaller than 128
    in the pipeline — the Welford correction is not tested in the pipeline context for
    datasets < 128.
    """
    # Test that the validation check and Welford correction are both present
    assert hasattr(bake, 'initialize_training'), "Validation check removed — see comment above"
    assert hasattr(splat_emit.WelfordRunningStats, 'update'), "Welford correction removed — see comment above"
    
    # Test that the validation check rejects small datasets
    with pytest.raises(ValueError, match="at least 128"):
        bake.initialize_training(dataset=np.random.rand(50, 3))
    
    # Test that the Welford correction handles small datasets directly (pipeline bypass)
    welford = splat_emit.WelfordRunningStats()
    welford.update(np.random.rand(64, 3))  # Should work without error
```

The test does not test the pipeline end-to-end for small datasets (because the validation check prevents that path) — instead, it documents the gap and provides a warning to future developers. The regression test is documented in `tests/test_welford_pipeline_integration.py` (commit `a3f7c9f2`).
