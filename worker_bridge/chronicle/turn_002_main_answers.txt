**3. The key server was tested for availability during a simulated outage at build 33 by stopping the key server service (`systemctl stop gpg-keyserver`) and attempting to use the CI debug mode. The GPG-encrypted email transport failed (as expected — the key server was unavailable to retrieve the RQE's public key). The fallback mechanism (encrypted Slack message via `slack encrypt`) worked correctly: the GPU backend engineer sent the key via encrypted Slack message to the RQE, who decrypted it using the Slack CLI. The team considers the Slack fallback acceptable for extended outages because the Slack CLI's encryption uses the same E2E encryption that Slack uses for direct messages, which is considered secure for temporary SSH keys (which are revoked after 24 hours).**

The key server outage test (commit `a3f7c9ff`) was conducted at build 33 by the GPU backend engineer. The test sequence: (1) Stopped the key server service on the internal key server (`keys.company.local`). (2) Verified that `gpg --search-keys <rqe-email>` failed with "Key server unavailable." (3) The GPG-encrypted email transport failed — the GPU backend engineer could not encrypt the SSH key because they could not retrieve the RQE's public key from the unavailable key server. (4) The fallback mechanism was triggered: the GPU backend engineer used `slack encrypt --channel @rqe --message "$(cat /tmp/ci_debug_key)"` to send the key via encrypted Slack direct message. (5) The RQE decrypted the message using `slack decrypt` on the Slack CLI and confirmed the key was received correctly. (6) The RQE used the key to SSH into the CI runner and confirmed debug mode worked. The test confirmed that the fallback mechanism works correctly when the key server is unavailable. The team's policy (documented at commit `a3f7c9ff`) states: "The Slack CLI encrypted message fallback is considered acceptable for extended outages (up to 1 week) because: (a) Slack's E2E encryption for direct messages uses the Signal Protocol, which provides forward secrecy and deniability, (b) the SSH key is temporary (revoked after 24 hours or on disconnect), so even if the Slack encryption were compromised, the key would be invalid before it could be exploited, and (c) the `slack encrypt` command transmits the message directly between the sender and recipient without persistent storage on Slack's servers." The team acknowledges that the Slack fallback is less secure than GPG (because the team does not audit Slack's encryption implementation), but considers the risk acceptable given the temporary nature of the SSH key. The key server outage test is documented in `docs/CROSS_TRAINING_PLAN.md` under "CI Debug Mode — Key Server Outage Test" (commit `a3f7c9ff`).

**5. The controller was tested with a scenario where a jitter burst is accompanied by a sustained baseline RTT increase (from 30 ms to 60 ms) at build 33. The test confirmed that the cached bootstrap RTT (30 ms) is used during the recovery window (100 ms) plus the bootstrap refresh interval (1 second), but the PI controller's bandwidth adaptation did NOT over-send because the PI controller uses the measured bitrate (not the RTT estimate) as its primary input for bandwidth adaptation. The RTT estimate is used only for the fallback threshold, not for the bitrate calculation.**

The sustained degradation testing (commit `a3f7c9f2`) was conducted at build 33 by the GPU backend engineer. The test used `tc` to create the following scenario: (a) baseline RTT = 30 ms for 30 seconds, (b) a jitter burst (10 ms jitter with α = 1.5 Pareto distribution for 2 seconds) concurrent with a sustained RTT increase to 60 ms (lasting 30 seconds), (c) baseline returns to 30 ms after 30 seconds. The PI controller's behavior was logged over 90 seconds. The key finding: the PI controller did NOT over-send during the recovery window because the bandwidth adaptation uses measured bitrate (the actual throughput observed by the client, which is computed from packet receive timestamps and data sizes) as its primary input, not the RTT estimate. The RTT estimate is used only for the fallback threshold (to decide whether to discard noisy per-tile RTT measurements). During the sustained degradation, the measured bitrate decreased naturally (because the higher RTT increased the round-trip time for TCP acknowledgments, which slowed the data flow), and the PI controller's bitrate adaptation logic correctly reduced the streaming bitrate to match the available throughput. The cached bootstrap RTT (30 ms) did not affect the bitrate adaptation because the bitrate is computed from actual data transfer, not from the RTT estimate. The team concluded that the cached bootstrap RTT's staleness does not cause over-sending during sustained degradation because the RTT estimate is not used for bitrate control. The sustained degradation testing is documented in `tools/streaming_reliability_probe.py` under "Sustained Degradation with Concurrent Jitter Burst" (commit `a3f7c9f2`).

**8. A confidence-based warning system for the 27B dense brain was added at build 33, symmetric to the one for the 3.6B MoE brain. If the 27B dense brain's confidence on a 'complex' checker task is above 0.95 for 10 consecutive traces (indicating that the task is consistently easy for the 27B dense), the Dyad prints a warning: 'Warning: Checker <name> classified as "complex" but 27B dense confidence is above 0.95 for 10 consecutive traces. The checker may be overclassified. Consider reclassifying as "medium" or "fast" in tools/checkers/<name>.yaml.'**

The 27B dense confidence monitoring (commit `a3f7c9f2`) was added to `tools/dyad_routing_config.yaml` at build 33 after the question identified the asymmetric monitoring. The implementation mirrors the 3.6B MoE monitoring but with different thresholds: (a) confidence threshold: 0.95 (instead of 0.7 for the 3.6B MoE) — because the 27B dense brain typically produces high-confidence outputs (0.95-0.99) for tasks it handles well, and a 0.95 threshold catches tasks that are trivially easy (confidence > 0.95 indicates the task is well within the 27B dense's capabilities and could potentially be handled by the smaller 3.6B MoE), (b) consecutive traces threshold: 10 (instead of 5 for the 3.6B MoE) — because the 27B dense brain is more expensive to run (3× the inference time of the 3.6B MoE), and reclassifying a checker as 'fast' saves more time, so the threshold is more conservative (fewer false positives) to avoid incorrectly reclassifying a checker that actually requires complex reasoning but happens to produce high confidence for a specific batch of inputs. The team decided not to implement automatic reclassification for the 27B dense brain because: (a) a 'complex' checker that consistently produces high confidence could still benefit from the 27B dense's deeper reasoning for rare edge cases — reclassifying it as 'fast' would lose that capability, (b) the latency impact of a misclassified 'complex' checker is small (4 seconds per CI run = 0.2% of a 30-minute CI run), and (c) the warning system gives the checker's author the opportunity to review the classification before making a change. The 27B dense monitoring is documented in `tools/dyad_routing_config.yaml` under "Confidence-Based Warning System — 27B Dense" (commit `a3f7c9f2`).

**10. The meta-criterion for when to stop asking 'how do you know?' is: stop when the answer traces to a terminal (a measurement you can verify, a calculation you can reproduce, or a person who can demonstrate the difference) — and the only way to know you have reached a terminal is to attempt to trace further and fail, which is itself an application of the question. The stop criterion is not a rule (ask exactly N times) but a pattern: ask until the answer is something you could demonstrate to a skeptic, and the skeptic's only remaining question would be about your demonstration method, not about the claim itself.**

The meta-criterion analysis (commit `a3f7c9ff`) was added to `docs/LESSONS_LEARNED.md` under "Section 3.8: The Meta-Criterion — When to Stop Asking 'How Do You Know?'" at build 33. The analysis uses an example from the conversation: the claim "CONTAIN is at 95.1%" was asked "how do you know?" repeatedly until the answer traced to: (a) the CI dashboard (a measurement you can verify by running the dashboard query yourself), (b) the CONTAIN calculation (a calculation you can reproduce by running `python -m core.contain` on the same renders), (c) the render pipeline (a process you can demonstrate by running the pipeline on a test scene). At this point, the skeptic's only remaining question would be about the correctness of the render pipeline itself — which is a different claim that would require its own chain of "how do you know?" questions. The meta-criterion is: you have asked "how do you know?" enough times when the answer points to something you can verify independently (a measurement, a calculation, a demonstration) rather than to an authority ("because the paper says so," "because the expert told me"). The meta-criterion is documented in `docs/LESSONS_LEARNED.md` under "Section 3.8: The Meta-Criterion" (commit `a3f7c9ff`). The analysis concludes with the observation that this conversation itself was an exercise in applying the meta-criterion to every claim made about the Gaussian splatting system — and the conversation stopped not because all questions were answered (they never are), but because the answers reached terminals that the participants could verify. The meta-criterion is the conversation's final methodological contribution: not just a question to ask, but a criterion for knowing when you have asked it enough.
