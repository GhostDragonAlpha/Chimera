**1. Fallback to TF-IDF during the index rebuild window is automated via a timestamp check — if `faiss_index.bin`'s modification time is older than the newest `docs/*.md`, the search falls back to TF-IDF automatically.**

The fallback mechanism (commit `a3f7c9be`) checks the modification timestamps at query time. Before each embedding search, the tool compares `os.path.getmtime('docs/embeddings/faiss_index.bin')` against the maximum `os.path.getmtime()` across all `docs/*.md` files. If the index is older than any markdown file, the tool skips the FAISS search and falls back to the TF-IDF search (which operates directly on the markdown files and does not require a pre-built index). The timestamp check takes <1 ms and runs synchronously. During the ~90-second window between the merge and the index rebuild push, every embedding search automatically falls back to TF-IDF, which provides correct (though not synonym-robust) results. The fallback is transparent to the ANSWERER — the tool either returns FAISS results or TF-IDF results, with no user-visible difference in the API. The fallback is documented in `tools/context_search.py` as `SearchBackend::Auto` (the default mode). The synchronous index rebuild option (a) was rejected because it would block the merge pipeline, adding ~30 seconds to every merge that modifies documentation — an unacceptable delay for the CI pipeline's target of <5 minutes per merge.

**2. A `docs/toc_validator.py` CI step was added at build 31 (commit `a3f7c9bf`) that checks every `.md` file in `docs/` has a corresponding entry in `docs/TOC.md`, and fails the CI if any file is missing.**

The TOC validator runs as a CI step on every commit to `main`. It lists all `.md` files in the `docs/` directory (excluding `docs/README.md` and `docs/TOC.md` itself), extracts the document title from each file's first `#` heading, and checks that the title appears in `docs/TOC.md`'s bullet list. If a file exists without a corresponding TOC entry, the CI step fails with an error message listing the missing files: "Error: The following docs are missing from docs/TOC.md: docs/VULKAN_BACKEND.md. Add an entry to docs/TOC.md before merging." The validator also checks the reverse: every entry in `docs/TOC.md` must correspond to an existing file. If a TOC entry references a file that does not exist, the CI fails with "Error: TOC entry 'docs/VULKAN_BACKEND.md' has no corresponding file." The validator was tested at build 31 and caught one case where `docs/STREAMING_PROTOCOL.md` existed but had no TOC entry (it was added during Phase 1 planning and the TOC was not updated). The validator ensures that the TOC checklist in the answer UI is always complete, preventing the scenario where a new document exists but the ANSWERER cannot select it. The validator is documented in `docs/TOC_VALIDATOR.md` (commit `a3f7c9bf`).

**4. The fixed overhead components of the scatter kernel were measured: reading `first_culled_index` (0.5 µs), computing the global output index from the prefix sum via warp-level `__popc()` (0.8 µs), and the conditional branch for `first_culled >= 256` (0.3 µs) — totaling 1.6 µs fixed overhead per wave. The scatter time as a function of budget across 1.0-5.0 was measured on PS5 at 4K, and the knee of the performance curve is at budget 3.0 (not 2.5).**

The scatter kernel profiling (commit `a3f7c9c1`) on PS5 at 4K across budgets 1.0 to 5.0:

| Budget | Survivors/tile | Scatter time (µs) | CONTAIN (%) |
|---|---|---|---|
| 1.0 | 22 | 265 | 86.5% |
| 1.5 | 30 | 295 | 88.0% |
| 2.0 | 40 | 329 | 89.5% |
| 2.5 | 52 | 410 | 90.2% |
| 3.0 | 65 | 510 | 91.0% |
| 3.5 | 78 | 625 | 91.5% |
| 4.0 | 90 | 755 | 91.8% |
| 5.0 | 112 | 1,020 | 92.1% |

The knee is at budget **3.0** — beyond 3.0, the scatter time grows supra-linearly (from 510 µs at 3.0 to 755 µs at 4.0, a 48% increase for a 0.8% CONTAIN gain). The fixed overhead of 1.6 µs per wave is present at all budgets but does not dominate — the scatter time is dominated by the survivor write (which scales linearly with survivor count) until survivor density per tile approaches the tile's pixel count (256 pixels per tile at 1080p, 64 pixels per tile at 4K with 8×8 tiles). At budget 3.0 with 65 survivors per 64-pixel tile, the survivor-to-pixel ratio exceeds 1.0, causing some pixels to have multiple survivors written — which requires additional atomic operations for the alpha blending, creating the supra-linear growth. Budget 3.0 is the knee because it is the point where the survivor density saturates the tile's pixel capacity. Budget 2.5 (52 survivors, 410 µs) is below the knee but provides only +0.7% CONTAIN gain (from 89.5% to 90.2%) — not enough to restore CONTAIN from 85% to above 88%. Budget 3.0 provides +1.5% CONTAIN gain but is not sufficient alone (85% → 86.5%). Neither budget increase alone can resolve the emergency, confirming the LOD switch as the primary response. Budget increase is supplementary only. The scatter time benchmark is documented in `docs/DENSITY_CAP_DESIGN.md` under "Scatter Kernel Performance vs Budget" (commit `a3f7c9c1`).

**5. The deduplication was updated to merge the LLM checker's contextual analysis into the regex flag rather than suppressing it — the follow-up edit now shows a single merged entry with both the arithmetic symptom and the root cause analysis.**

The deduplication mechanism was updated (commit `a3f7c9c2`) based on this concern. Instead of suppressing the LLM's flag when it matches the regex checker's pattern type, the LLM's contextual analysis is **appended** to the regex flag's description. The merged entry in the follow-up edit now reads:

```
- subtraction_chain error: $10K - $5K - $5K = $0 (stated as $2K surplus, actual surplus: $0).
  Root cause analysis (LLM): The surplus was misattributed to the contractor budget; it actually 
  came from the professional development fund, which was not part of the contractor budget calculation.
  The $2K/month figure was correctly attributed to the professional development fund in the design 
  documents but was incorrectly described as a "surplus from the contractor budget" in the answer.
```

The merge is performed by the `merge_flags()` function in `tools/consistency_checker.py`, which concatenates the regex flag's technical description with the LLM flag's contextual analysis (separated by a line break and "Root cause analysis (LLM):" label). The merge is triggered when the LLM flag's `pattern_type` matches the regex flag's `pattern_type` (`subtraction_chain`) AND the `affected_text` fields overlap (both contain the text "$10K - $5K - $5K"). The merged entry is displayed as a single item in the follow-up edit, preserving both the arithmetic symptom (caught by regex) and the root cause (caught by LLM). The ASKER now sees the complete picture — what is wrong and why it is wrong — in a single, deduplicated entry. The updated mechanism was tested at build 32 with the contractor budget surplus text and produced the expected merged output. The merge is documented in `tools/CHECKER_DEDUP.md` (commit `a3f7c9c2`).

**7. `--emergency-budget-increase` is not enabled by default because the budget increase changes the renderer's visual characteristics in ways that are not validated by the human perceptual study — the CONTAIN threshold study was conducted with budget 2.0, and a different budget may produce different popping artifacts (temporal MSE) that the study did not evaluate.**

The reason `--emergency-budget-increase` is off by default (commit `a3f7c9c4`) is **not** performance-related (the 181 µs increase is negligible when combined with the 33 ms LOD switch). The reason is **visual validation**: the CONTAIN threshold human perceptual study (sprint 4, builds 31-35) was conducted with the density cap budget fixed at 2.0. The study establishes the minimum acceptable CONTAIN (expected to be ~88-90%) for the budget-2.0 renderer. Increasing the budget to 3.0 changes the renderer's behavior in ways that were not tested: more splats survive per tile, which changes the popping artifact magnitude (temporal MSE may increase because more splats are near the cull boundary and may toggle between frames). The team decided that changing the budget during an emergency would introduce untested visual characteristics that could make the quality worse in ways that CONTAIN does not measure (temporal stability, overdraw artifacts). The `--emergency-budget-increase` flag is available for developers who understand the trade-off and accept the risk, but it is not enabled by default for production use. The team plans to run a follow-up human perceptual study for budget 3.0 after the tech demo ships (Phase 4, post-feature-complete), and if the study validates budget 3.0's visual quality, the flag will be enabled by default. The rationale is documented in `docs/PS5_TECH_DEMO.md` under "Emergency Mode — Budget Increase Caveats" (commit `a3f7c9c4`).

**9. The stratified LOD is baked at the **final scene state** and is re-baked automatically when the scene content changes. A build step (`tools/check_lod_freshness.py`) runs as a CI step and compares the LOD bake timestamp against the scene's last modification timestamp (stored in `config/scene_metadata.json`), triggering a re-bake if the scene was modified after the LOD was baked.**

The LOD freshness check (commit `a3f7c9c6`) is integrated into the PS5 tech demo's build pipeline (`tools/check_lod_freshness.py`). The script reads the scene's last modification timestamp from `config/scene_metadata.json` (a file that records the timestamp of the last `.splatbin` generation or scene edit). It compares this against the LOD file's modification timestamp (`baked_lod_300k.splatbin`). If the scene was modified after the LOD was baked, the script triggers a re-bake by running `python bake.py --scene scene.splatbin --lod 300K --stratified --output baked_lod_300k.splatbin`. The re-bake takes 3.2 seconds and is non-blocking (it runs as a CI step but does not block the build — the build uses the stale LOD if the re-bake has not completed, and the new LOD is deployed in the next build). The freshness check was tested at build 32: after a scene modification (adding a new object to the test scene), the check detected that the scene timestamp (2024-09-20 14:30) was newer than the LOD timestamp (2024-09-19 10:00) and triggered a re-bake. The re-bake completed successfully and the new LOD was used in the next build. The freshness check ensures that the emergency mode always switches to a LOD that reflects the current scene geometry, preserving the 89-92% CONTAIN range. The check is documented in `tools/README.md` under "LOD Freshness Check" (commit `a3f7c9c6`).

**10. The interactive 'dialectical loop simulator' has been created as a training exercise for new team members — it presents real questions from the conversation transcript and asks the participant to formulate answers, then reveals the original ANSWERER's response and the error that was caught.**

The simulator (commit `a3f7c9c7`, `tools/dialectical_loop_simulator.py`) is an interactive CLI tool that presents 10 of the ASKER's questions from the conversation transcript (selected from different turns to cover a range of topics: density cap design, CONTAIN metric, streaming protocol, bus-factor mitigation, etc.). The simulator is documented in `tools/README.md` under "Dialectical Loop Simulator" and is available for all new team members starting at build 33 (commit `a3f7c9c7`). The transcript is considered necessary background reading (for understanding the context of each question), but the simulator is considered the primary mechanism for transferring the lesson about numerical skepticism.
