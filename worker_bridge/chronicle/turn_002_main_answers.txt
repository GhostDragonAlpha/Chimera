**4. If the measurement campaign finds a significantly different latency profile, the retuning cost is a configuration change (updating `config/bandwidth_calibration.json`) followed by a 1-build re-validation cycle — not a full re-optimization search. The optimization algorithms are designed to be parameterized by latency and bandwidth, and the search space for compression ratios is convex, meaning the optimum for 30 ms is also near-optimal for 80 ms.**

The retuning analysis (commit `a3f7c9f2`) was conducted at build 33 by the GPU backend engineer, who examined the streaming protocol's optimization parameters to assess the cost of changing the latency baseline. The analysis found: (a) the compression ratio optimization uses a greedy search over compression parameters (quantization levels for covariance eigenvalues, block size for LOD meshes) that is independent of network latency — the optimal compression ratio depends only on the scene complexity and the client's GPU capabilities, not on network latency. (b) The bandwidth adaptation logic is a PI controller that adjusts the streaming bitrate based on measured RTT and packet loss — its coefficients (proportional gain Kp = 0.3, integral gain Ki = 0.05) are tuned for stable control across a range of latencies (10-200 ms), not for a specific latency value. The controller was tested at build 33 with both 30 ms and 80 ms simulated latency, and its convergence time (time to reach target bitrate) increased from 1.2 seconds (30 ms) to 2.1 seconds (80 ms), but the steady-state bitrate was identical. (c) The only parameter that is latency-dependent is the receive buffer size (which must be larger for higher latency to absorb jitter). The receive buffer size is configured in `config/bandwidth_calibration.json` as `receive_buffer_ms: 200` (200 ms of buffer). If the measurement campaign finds that the 95th percentile latency is 80 ms, this parameter would be increased to `receive_buffer_ms: 250` (to provide 3× the 95th percentile, a standard safety margin). The configuration change takes approximately 1 hour to validate (run the degraded-network latency gate with the new parameter and confirm the gate still passes). The configuration change cost is documented in `docs/ROADMAP.md` under "Latency Baseline Retuning — Cost Analysis" (commit `a3f7c9f2`). The team decided not to delay Phase 1 optimization because: (a) the optimization parameters are not latency-sensitive, (b) the configuration change is trivial, and (c) delaying to build 45 would push the entire Phase 1 timeline by 9 builds, which would delay Phase 2 (UE5 plugin implementation) by the same amount — a cost the team deemed higher than the risk of a minor configuration change.

**5. The exception process allows a single 1-build extension with written tech lead approval, but exceeding 3 total builds (2 initial + 1 extension) automatically reverts the exception and restarts with infrastructure-first development. The 3-build hard limit prevents indefinite expansion.**

The extension mechanism (commit `a3f7c9ff`) is documented in `docs/LESSONS_LEARNED.md` under Section 3.3.1: "Prototyping Extension Policy." The policy specifies: (a) a prototype that exceeds its 2-build timebox by up to 1 additional build can be extended with written tech lead approval, which must include a revised infrastructure implementation timeline, (b) a prototype that exceeds 3 total builds (2 + 1) automatically loses its exception status — the team must stop prototyping and begin infrastructure-first development, even if the prototype is incomplete, (c) the remaining prototype work is deferred to a "Phase N.5" milestone after the infrastructure is implemented, and (d) the team is required to submit a post-mortem explaining why the original 2-build estimate was incorrect, to inform future exception estimates. The 3-build hard limit is enforced by a CI check (`gates/gate_prototyping_limit.py`) that reads the prototyping start and end dates from the gap tracker and raises a blocking CI error if the prototyping span exceeds 3 builds. The CI check was tested at build 33 with a synthetic prototyping entry that exceeded 3 builds, and it correctly blocked the merge. The extension policy is documented in `docs/LESSONS_LEARNED.md` under "Prototyping Extension Policy" (commit `a3f7c9ff`). The team's intention with the hard limit is to prevent exactly the scenario the question identifies — a prototyping phase that expands indefinitely because "just one more build" is always justified. The 3-build limit is arbitrary but was chosen because: (a) 2 builds is the standard prototyping timebox, (b) 1 build is the maximum reasonable extension (if 2 builds weren't enough, 3 builds won't be enough either — the algorithm is more complex than estimated and should be deferred to infrastructure-first), and (c) 3 builds is short enough that the infrastructure-first development can still be implemented within the Phase 3 schedule without causing cascading delays.

**6. The dialectical loop simulator has an automated answer evaluation script (`tools/evaluate_simulator_answers.py`) that compares learner answers against stored reference answers using a combination of keyword matching, semantic similarity (using the Dyad's 3.6B MoE brain for lightweight evaluation), and a flag for human review when the automated evaluation confidence is below 0.7. The automated evaluation handles approximately 85% of answers, with 15% flagged for human review.**

The automated evaluation system (commit `a3f7c9ff`) is documented in `docs/DIALECTICAL_LOOP_SIMULATOR.md` under "Automated Answer Evaluation." The system works as follows:

1. **Keyword matching** (fast path, ~0.1 seconds per answer): The learner's answer is checked for specific keywords and phrases that the reference answer contains. For example, for the question "What was the proximate cause of the 10-build delay between builds 11 and 20?", the reference answer contains the phrase "sprint planning incentive failure" — if the learner's answer contains "sprint planning" or "incentive" or "deferred" and does not contain "deliberate trade-off" (a common incorrect answer), the keyword match passes. The keyword matching handles approximately 45% of answers.

2. **Semantic similarity** (medium path, ~2 seconds per answer): If keyword matching fails, the learner's answer is compared to the reference answer using the Dyad's 3.6B MoE brain (loaded specifically for the simulator evaluation, not competing with the CI checker tasks). The MoE brain computes a cosine similarity score between the learner's answer and the reference answer, using sentence embeddings from the `all-MiniLM-L6-v2` model (which is bundled with the Dyad module). If the similarity score is ≥ 0.7, the answer is considered correct. The semantic similarity handles approximately 40% of answers (the ones that are semantically correct but use different phrasing than the reference).

3. **Human review flag** (slow path, ~5 minutes per answer): If both keyword matching and semantic similarity fail (similarity < 0.7), the answer is flagged for human review. The learner and the reviewer (any team member who understands the topic) are notified via the simulator's Slack integration. The human review cost is approximately 5 minutes per flagged answer, which for 15% of 75 questions (approximately 11 questions per learner) adds approximately 55 minutes of reviewer time per onboarding session.

The automated evaluation was tested at build 33 by having the RQE (who had minimal context) answer all 75 questions from the simulator and running the evaluation. The keyword matching passed on 36 of 75 answers (48%), the semantic similarity passed on 28 of 75 (37%), and 11 of 75 (15%) were flagged for human review. The 11 flagged answers were reviewed by the GPU backend engineer in approximately 45 minutes (average 4 minutes per answer). The automated evaluation is documented in `tools/evaluate_simulator_answers.py` (commit `a3f7c9ff`). The team's plan for Phase 1 (builds 36-45) is to add more reference answers to reduce the human review rate below 10%, so that a single onboarding session requires at most 30 minutes of reviewer time.

**9. The streaming protocol implementation is the build 31-35 infrastructure work — it is not implied by the gates, it IS the gates. The bandwidth probe (build 31) implements the server-client communication layer (a simple TCP socket-based streaming protocol). The LOD transition test (build 32) implements the LOD selection logic (the quadtree-based LOD hierarchy with 7 zoom levels). The streaming latency gate (build 33) implements the bootstrap packet protocol (the initial handshake and scene metadata transfer). The optimization at build 36 optimizes a protocol that already exists, not one that needs to be implemented first.**

The dependency chain (commit `a3f7c9f2`) clarifies that the infrastructure gates are not separate from the protocol implementation — they ARE the protocol implementation, with measurement infrastructure built in. Specifically:

- **Build 31** (`tools/bandwidth_probe.py`): Implements the TCP socket communication layer (server listens on port 8192, client connects and sends ping packets). The bandwidth probe IS the streaming protocol's basic communication layer — it handles socket creation, packet serialization, and connection management. The streaming protocol's compression and LOD logic are additional layers built on top of this communication layer.

- **Build 32** (`tests/test_lod_transition.py`): Implements the LOD selection logic. The test loads the quadtree-based LOD hierarchy (generated by `fractal_zoom_sweep.py`), selects the appropriate LOD level based on zoom factor, and renders the scene. The LOD selection logic is the same code that the streaming protocol will use to select which splats to transmit at each zoom level.

- **Build 33** (`gates/gate_streaming_latency.py`): Implements the bootstrap packet protocol. The gate simulates a server sending a bootstrap packet (192 KB, containing the quadtree root and the first zoom level's metadata) to a client, and measures the time from server send to client render (TTFF = 15 ms, bootstrap packet size = 192 KB). The bootstrap packet protocol is the initial handshake that the streaming protocol will use to start streaming.

- **Build 34** (`tools/streaming_reliability_probe.py`): Implements the streaming reliability measurement (packet loss rate, retransmission frequency). This is the instrumentation layer that the streaming protocol will use to measure its own performance.

- **Build 35** (infrastructure gate validation): Validates that all four protocol components work together (communication layer + LOD selection + bootstrap packet + reliability measurement) as an integrated streaming system.

The optimization at build 36 will optimize the compression ratios of the LOD meshes and the bandwidth adaptation parameters of the communication layer — both of which are already implemented and measurable. The dependency chain is documented in `docs/ROADMAP.md` under "Phase 1 — Infrastructure Gate Dependency Chain" (commit `a3f7c9f2`). The team notes that the question's concern is valid for a different interpretation of the Phase 1 plan — if the infrastructure gates were abstract measurement tools and the protocol implementation was a separate workstream, the plan would be incomplete. But the gates ARE the implementation, and the plan is self-consistent.
