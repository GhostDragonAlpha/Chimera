P2. STATEMENT OF THE SWEEP
- Extraction sources: every file under docs/evidence/ (self-exclusion
  above applied) whose extension is in the text whitelist
  {json, txt, md, log, py, sha256, jsonl, html, diff, patch, source,
  ps1, csv, yml, yaml}. Every extension found under docs/evidence/ that
  is NOT whitelisted is counted in a coverage table in the findings
  (never silently dropped; this is the anti-"hash classes silently
  skipped" guard at the source level).
- A reference is a (recorded_sha256, file_path) association found by the
  extractor classes in P3. Only sha256-class hashes are recomputed:
  exactly 64 hex digits ([0-9a-fA-F]{64} with non-hex boundaries).
  Shorter/other digests (e.g. 40-hex git sha1, 8-hex truncated prose
  digests) are out of scope by definition and appear only in the
  coverage counts of encountered hex-token lengths, so no hash class is
  silently skipped.
- Three headline counts (the packet's "three counts"):
    matched      = reference path exists and recomputed sha256 equals
                   the recorded hash (case-insensitive)
    mismatched   = reference path exists and recomputed sha256 differs
    missing_file = reference path recorded but no candidate resolution
                   exists on disk
  Auxiliary counts, reported alongside and never merged into the three:
    out_of_tree  = resolved absolute path outside this repo root
                   (e.g. E:\ChimeraWork\slot-03\... written by another
                   slot; recomputing there is not tree integrity)
    unassociated = 64-hex token with no file path the extractor may
                   defensibly bind (e.g. runtime state ids, stdout
                   digests, data-array digests with no path). Enumerated
                   one line per instance in the raw table.
    unresolvable = path association found but truncated by the original
                   capture tool (e.g. Get-FileHash Format-Table
                   ellipsis "...") so no deterministic candidate exists.

P3. EXTRACTION CLASSES (fixed, deterministic)
  C1 sha256sum_line : text line "<hex64> [marker]<path>" (sha256sum/cksum
     convention); path resolved relative to the sidecar's directory,
     then the repo root.
  C2 line_path_token: same line contains the hex64 and exactly one other
     path-like token (contains '/' or '\' or a dot-extension; not a URL
     scheme, not itself hex) -- covers Get-FileHash tables and inline
     "SHA256 <hash> <path>" rows. Resolution as C1; absolute paths
     classified per P2.
  C3 json_key_path  : parsed JSON object whose KEY is a path-like string
     and whose VALUE is exactly 64 hex digits (source manifests).
  C4 json_sibling   : parsed JSON object with a 64-hex value under key K;
     sibling binding searched in priority order: exact keys
     path/file/filename/filepath/location/artifact; then K with a
     '_sha256'/'sha256' suffix stripped plus _path/_file/_filename; then
     any sibling key ending _path/_file/_filename (sorted, first wins).
  C5 named_sidecar  : file named "X.sha256" whose whole content is one
     bare hex64 -- binds to sibling "X" in the same directory (the
     convention the artifact itself is named by).
  C6 labeled_nearby : hex64 on a line carrying a sha256-ish label but no
     same-line path; searches at most the 3 previous and 2 following
     non-empty lines for "file|path|filename : <path-like token>".
     Conservative: bare unlabeled path tokens in prose are never bound.
  Anything not bound by C1-C6 is `unassociated`. First class that binds
  wins (deterministic); the raw table records which class bound.

P4. RESOLUTION AND RECOMPUTATION RULES
- Path normalization: backslashes to slashes; strip surrounding quotes,
  angle brackets, and trailing punctuation.
- Absolute paths inside this repo root resolve to their repo-relative
  form; absolute paths outside -> out_of_tree.
- Relative candidates tried in fixed order: <sidecar_dir>/<path>, then
  <repo_root>/<path>. Neither exists -> missing_file.
- Recomputation: hashlib.sha256 over the target file's raw bytes. The
  single recorded normalization variant ("sha256_crlf_normalized_to_lf")
  is recomputed with b"\r\n" -> b"\n" applied first; no other transform
  is guessed at. Comparison case-insensitive.

During script bring-up, inspecting extraction behavior on the retained
tree revealed two token-wrapping conventions the P3/P4 rules did not
cover, each causing a recorded reference to fail resolution purely
because of wrapper characters (never because of content):

  A1-a  markdown backtick-wrapped tokens, e.g. a line of the form
        "- `path`: `<hex64>`," -- the path token arrives wrapped in
        backticks and followed by a colon. The original single-pass
        strip could leave the closing backtick after the colon was
        stripped (strip order artifact), mis-resolving the reference.
  A1-b  sha256sum binary-mode markers, e.g. manifest lines of the form
        "<hex64> *path" -- the leading '*' is the sha256sum binary-mode
        convention, not part of the path.

AMENDED RULES (supersede the corresponding parts of P4 only):
- norm_path strips the character set {quote, apostrophe, backtick,
  asterisk, angle/curly/square brackets, trailing punctuation} to a
  FIXPOINT (repeat until stable), so wrappers compose correctly. No
  other resolution or recompute rule changes.
- Fixture extended with fixture/backtick_table.md exercising A1-a with
