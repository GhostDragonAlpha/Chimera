STATEMENT (disagreeable)
------------------------
The frozen engine drives the product's motion through state planes that are
mostly INVISIBLE in the rendered frame, and this is classifiable from the HTTP
contract alone into exactly three planes-of-existence: (a) already-visualized
(the engine itself renders pixels for it), (b) renderable-but-inactive (a
render path exists in the contract but is not active in the served frame), and
(c) data-only (JSON state that drives or reports motion, with no rendered
trace anywhere). Furthermore, a viewer-only Python layer can give the
motion-driving data-only planes the two-phase visibility lifecycle — visible
for verification, invisible once proven, user-toggleable — with ZERO C++
edits, because the engine already serves the state over HTTP and composites
overlays over /glass.
