2026-09-30, the Captain (after the Astra consultation) decided the workflow-automation program:

**Priority: acceptance-chain orchestration first.** The session's incident set (six hand-assembled chains; wrong-head, stale-re-record, missing agent_id, GitHub-lag failures) justifies it — but incidents are not proof the tool eliminates the classes; the SIX FAILURE TESTS are the bar: changed head, changed criteria, altered evidence, duplicate submission, delayed GitHub visibility, crash-after-external-action-before-receipt.

**The correction that governs everything:** "implemented in code" ≠ "operationally closed." Retention is NOT solved until actual workspace release and bypass counts are measured. Apply the same standard to all five movers (acceptance chain, job submitter, generated bodies, reviewer factsheet, amendment/anchor tools).

**The five rulings (Astra-informed):**
1. Prereg generation can be a genuine commitment: the boundary is WHEN choices fix relative to seeing results, not who typed it. Generate identifiers/units/schema/provenance/commands; an accountable author approves claim+competing-explanation, prediction+falsifier, threshold derivations/exclusions/stopping rules, and which observations already informed the choices. Freeze spec AND generator version before the confirmatory run. Label probes EXPLORATORY; test derived bounds on a separately declared validation set. A generator must never quietly choose a favorable threshold after reading validation results.
2. Reviewer factsheet: supply evidence, never the verdict. Observed (command→bytes) / Checked (bytes satisfy predicate) / Judged (experiment tests the claim) — only the reviewer supplies the third. Reviewers identify likely failure modes BEFORE reading conclusions. Independently reproduce the highest-consequence checks (running the same flawed checker twice ≠ independence). Reviewer must control what to challenge (NASA IV&V principle, adapted).
3. State machine: EXTEND the existing registry, never a competing authority. Bind transitions to card+attempt+criteria-hash+candidate-head+evidence-manifest-hash. Atomic updates, durable records, retry-safe external actions with reconciliation on lost responses. Keep parallel execution; centralize transition authority. Cancellation, supersession, storage release are real lifecycle states.
4. Acceptance stays an identifiable decision; its execution can later be automatic. First implementation: tool assembles+validates, STOPS at READY_FOR_ACCEPTANCE; decision-maker approves an immutable packet; tool records the decision. Later, explicit policy may delegate routine acceptance when required predicates + authorized independent review match the EXACT candidate. Amendments, disputed evidence, synthetic-to-REALITY classification, and operator taste decisions stay OUTSIDE delegation. One head's review never authorizes another head.
5. Build graph: `sealed receipts + authored interpretation + templates + generator versions → report → PR body`. Generated regions have ONE writer; authored interpretation is a separate versioned input; never hand-edit generated prose. Include criteria, capture context, schemas, formatter versions, environment identity in the graph. GitHub head/status are FRESH observations rechecked at transitions. Content-addressed storage ≠ retention: keep accepted evidence reachable from durable records; GC unreferenced intermediates.

**THE COMPILER DOCTRINE (the Captain's second doctrine, same day):** a compiler that produces EXECUTABLE WORK and BOUNDED QUESTIONS. Five outputs: RESOLVED / EXECUTE / RETRIEVE / ASK / BLOCKED. The key distinction: missing JUDGMENT vs missing EXECUTION - an unknown measurement triggers an experiment, a missing file triggers retrieval, NEITHER automatically becomes an AI question; an execution failure must never silently become permission to ask AI to guess. Bounded questions establish: the decision required, why rules/evidence cannot resolve it, available evidence, constraints, what changes on the answer, permitted answer kinds (+ AUTHORITY LIMITS). AI answers = REVIEWABLE PROPOSALS (decision/reasoning/evidence/assumptions/uncertainty/proposed-change/required-validation) - never auto-facts/amendments/approvals. Nine passes (Parse/Resolve/Check/Plan/Identify-gaps/Execute/Evaluate/Package/Finalize), each with inspectable outputs. Dependency law: never ask downstream questions on unsettled premises; invalidate only affected descendants; reuse answers only when inputs/criteria/scope match (never wording similarity). RULE PROMOTION: repeated stable decisions -> propose explicit rule -> test vs counterexamples -> review+version -> move from AI judgment into compiler checking; NEVER infer a universal rule from repeated similar answers. Rollout metrics include correctness guards (incorrectly-resolved questions + escaped defects) - never optimize tokens at correctness's expense. The development target: 'a system that knows why it is asking a question, supplies everything needed to answer it, and can check what the answer permits next.' First target = the acceptance chain, read-only vs completed cards.
