Shipped 2026-09-17 (master 14c56162, work.data.graph_store_split verified): the monolithic graph stores hit GitHub's hard 100 MB per-file ceiling at ~18k objects (intake-life measured 104.6/114.2 MB on a full apply). The split: **BULK_KINDS = {reference_entity, property_assertion, geometry_asset, mapping, relationship} shard; everything else (sources, work, model, doc, model_definition) stays in the single core.**

Architecture (durable facts for future sessions):
- **Authored side**: `data/authored/records/records_NNN.json` shards ({"objects":[],"relations":[]}); `project_program.json` stays small and hand-editable (~13 MB core). `build_graph.py` loads shards after the program and **defers ALL relation edges until every object from both sides is loaded** (program edges reference sharded endpoints — relating early raises "relation endpoint missing").
- **Compiled side**: `CreatureGraph.save()` packs bulk objects sorted-by-id into `creature_graph.bulk_NN.json` (~26 MB each, only when bulk > 24 MB — small/scratch stores stay single-file so tests are unaffected) and records the manifest in `meta["bulk_shards"]`; stale shards from earlier rotations are deleted. `load()` merges shards; **`merged_payload(path)`** gives raw-dict/snapshot consumers (e.g. test_force_compiler) the merged view — grep for direct `json.load(creature_graph.json)` readers when touching the store.
- **Apply routing**: `batch_qualify.apply_patches` sends new BULK_KINDS objects to the last shard (rotating at 24 MB) and the rest to the program — one serial writer preserved. **Post-appearance fix (2026-09-18): rotation is now PER-OBJECT on measured bytes** (was start-of-run only, which let the USGS bulk family write a single 125MB unpushable shard; the appearance lane fixed it with a falsified test using a patched 64KB threshold). Also: apply_patches now loads EVERY `records_*.json` shard for dedupe/immutability guards (the geo lane's repair, superseding the single-shard F5 form).
- `graph_hash` is computed over merged content, so **the falsifier is bit-identity: post-split rebuild reproduced the pre-split hash exactly (132e2922cf5ad313)**; consumer parity = graphify HONEST, five byte-identical re-proofs, funnel suite green, evidence 11/11.

Result: Rhea's 14,202 records admitted in the same session (18,023 verified, 0 contract failures) — **library 31,749 objects** (7× the morning's 4,518), largest file 55.3 MB, ceiling held with room.

**Why:** the ceiling was structural, not a tuning problem; sharding by object family keeps every consumer interface intact while removing the per-file limit.
**How to apply:** never append bulk records to project_program.json directly — let apply_patches route them; when writing a new raw store reader, use merged_payload(); when a future intake approaches ~90 MB per shard, lower SHARD_TARGET_BYTES rather than raising file limits.
